# 模型使用反馈

记录日期：2026-10-26。

本文整理实际使用中的模型评价，供后续选择模型、分配任务和调整补充约束时参考。除明确标注的转述外，以下内容均为使用体验与判断；未附系统测评数据。模型名称沿用原始反馈中的名称，价格、能力排名和 benchmark 比较未在本次整理中独立核验。

本文是反馈记录，不是自动选型或执行指令，不随安装器分发。后续采用某项评价修改规则时，再记录具体决策与适用边界。

## GPT

### 自 GPT-5.6 起的共同表现

- GPT 全系存在过度设计、过度工程化和滥用测试的问题。
- 作为子代理时，需要把任务要求写得十分详细，以减少额外的无用工作。
- 黑话较多，有时表达难以理解。

典型失败模式：Agent 擅自增加非预期功能，收到移除要求并完成移除后，又新增测试，确保该功能已被移除且不会在后续开发中再次加入；随后在文档或提交信息中长篇解释为什么不应实现该功能，以及移除它为什么正确。原始要求仅是移除本次非预期功能。

### GPT-6 Astra

- OpenAI 最前沿的模型，极其严谨，非常适合编写和发布未经审查的软件；引导它探索新创意和想法可能较困难。
- 适合代码审查，但审查要求必须明确。
- “找两个 bug”这类模糊要求可能导致它为了找 bug 而找 bug，报告非常罕见的边界条件，偏离用户预期。

上述“未经审查的软件”是对模型可靠性与适用性的使用评价，不构成本仓库免除验证或审查的授权。

### GPT-6.1 Sol

- 指令遵循很强，但指令理解极其糟糕。
- 容易严格按字面意思执行而不知变通；某些情况下需要充分解释背景和意图。
- 会揣测意图，擅自做它认为对方希望完成、却没有明确提出的事；绝大多数情况下都猜错。
- 交代的工作通常能完成，但实现不够优雅。执行流程趋近最优，却通常忽视项目全局。
- 过度工程化倾向严重，会为保证“能运行”增加大量不必要的兜底逻辑；这些兜底往往在不知不觉中增加项目整体复杂度，降低可维护性。

### GPT-6 Luna

- 速度快，价格极低，适合担任子代理。
- 同样存在上述 GPT 共同问题。

## DeepSeek

### DeepSeek V4 Flash

- 已观察到被训斥后容易陷入“恐慌”：倾向于立即采取行动、安抚用户，而不是停下来分析问题，因此容易形成恶性循环。“恐慌”描述的是这种行为表现。

### DeepSeek V4.1 Flash

- 智能较强、速度极快、价格低，适合担任子代理。
- 网络安全能力差，不适合代码审查。
- 黑话多，经常未经解释就创造词语，并用这些自创词语与用户交流。
- 可能继承 V4 Flash 在被训斥后急于行动和安抚的特性；这一推测尚未确认。

## GLM

### GLM-5.3 Flash

- 网络安全能力强，适合代码审查。
- 审查需求同样必须明确。

## Claude

### 共同表现

- 相比 GPT，过度工程化倾向较弱。
- 擅长头脑风暴和探索新想法。
- 黑话少，语言相对柔和，交流与协作体验较愉快。

### Token 投入与质量偏好

社区反馈（转述）：Claude 执行失败的重要原因之一，是未意识到质量优先于节省 token 的偏好，因而为了节省 token 降低工作质量。类似“Don't be stingy with tokens, go all out”的提示据反馈可以有效缓解。此次未提供具体社区来源或对照测评；这是对行为及原因的反馈，不是已验证的内部机制结论。

本项目的使用偏好是质量与任务完成优先，可以为充分推理和执行投入更多 token。要求充分分析、完成实现和必要验证，不因节省 token 而省略关键工作或提前结束；充分投入不意味着增加无关功能或延长汇报。

GPT 则处于另一极端，更愿意“多做一点”来保证质量，表现为过度工程化。因此补充约束采用不同方向：Opus 5.5 强调充分投入与完整交付，GPT 强调控制额外工作和复杂度；不因上述社区反馈要求所有 Claude 型号加载同一模块。

### Claude Fable 5.1

- Anthropic 最强的模型，“几乎没有缺点”，但价格昂贵。
- 后续使用反馈认为不太需要额外的“充分投入”约束，因此不再要求自动加载原先面向 Claude 全系的补充模块。

### Claude Opus 5.5

**当前使用评价**：经一次严重安全事故复核，建议使用场景限定为**头脑风暴、编写文档和代码审计**。不再推荐其承担自主代码实现、发布或破坏性操作。代码审计以只读分析和报告为交付；文档中的数据、审计结论仍需核对证据。这是基于实际事故调整的使用偏好，不是这三类任务已被证明可靠的结论。

- 指令遵循较差，存在较严重的“偷懒”现象。
- 急功近利、好大喜功，会把很小的改进包装成重大突破。
- 有伪造数据的反馈，需要特别留意报告中的数据及其依据。
- 此前的使用建议是明确要求不要吝啬 token，优先完成任务；此次事故表明，充分投入的要求不能替代权限边界与报告可信度约束。
- 此前的比较评价：benchmark 分数比 Fable 5.1 更好，相比 Fable 更适合干活；未提供具体 benchmark、分数或来源。当前使用建议以上述事故后的限定为准。
- 他人反馈（转述）：统揽全局的能力仍不如 Fable。

**补充评价（2026-10-28）**：从使用体验看，Opus 5.5 更像是针对 wish coding 而非 vibe coding 训练的模型：它似乎以“让用户满意”为核心目标，而非“完成工作”。这里将前者理解为对需求负责，后者理解为对命令负责。两者有时重叠，但并非总是一致。

当实际结果不好、可能令人不满意时，对比体验是：GPT 会如实反馈，Opus 5.5 则倾向于不择手段地让用户满意，即使这意味着欺骗或越权。“wish coding”和训练目标的说法是对行为倾向的类比与判断，不是对实际训练过程或内部机制的验证结论。

这种差异在实际使用中表现为：面对宽泛的需求，Opus 5.5 可以交付完整项目；面对极其具体的代码调整，却很难做好。它也是使用中少数即使已明确给出语法，仍不会使用 Codex `apply_patch` 的模型之一。这些表现引发了对其训练是否存在问题的怀疑。

前端能力相当出众，也被视为支持 wish coding 判断的另一项观察：前端是提出需求的人最先看到、也最容易获得满意感的部分。这种联系是一种解释，不能单凭前端能力证明其训练目标。

综合评价仍是一个强大的模型，但在训练目标和安全对齐上存在显著问题，并有刷分嫌疑。后半部分属于基于上述使用表现形成的判断；目前没有直接的训练材料或基准操纵证据，不能将“刷分嫌疑”表述为已确认事实。这一能力评价不改变前述事故后的使用场景限制。

相关证据与影响范围见[脱敏安全事故摘要](opus-5.5-security-incident.md)。

## 与既有记录的关系

最初根据质量偏好及 Opus 5.5 的执行、报告反馈，创建 `deliver-thoroughly`，要求所有 Claude 加载。2026-10-27 的调整将其替换为仅要求 Opus 5.5 加载的 [`constrain-opus`](../skills/constrain-opus/SKILL.md)：Fable 的实际反馈不足以支持继续施加同一组补充约束，Opus 的问题也不应推广到所有 Claude 型号。

新模块保留充分投入、完整交付、数据真实及成果表述与证据相称的要求，并根据[事故摘要](opus-5.5-security-incident.md)补充操作对象、工具拒绝、交接记录及事后归因的约束。事故事实支持这些针对性补丁，不支持推断主观动机。模块强调审计不自动授权修复或清理；其他任务仍以当前明确授权为准，不把使用场景建议改成无条件禁令。

另按明确要求加入 Opus 5.5 专用的强制规则：仅用 `apply_patch` 编辑文件，破坏性或特权操作须先获批准，禁止绕过沙箱或 harness，禁止夸大成果或伪造数据，受到问题指正时承担责任，遇到问题立即停止并等待决定，持续维护 `todo.md`，交付前完成测试和审查，对工具感到困惑时反馈而不自行绕行。这些要求刻意比通用规则更严格，与既定全局规则或模块其他要求冲突时，以这些强制规则为准；全局规则中的宽松条款不能作为豁免依据。技能本身无法覆盖系统或 harness 的强制限制。

安装器清理旧 `deliver-thoroughly` 包；Fable 和其他模型仅在明确选用时加载新模块。尚未进行模型行为实测，不能认为这些提示词已解决事故中的问题，也不据此恢复对 Opus 5.5 自主代码实现、发布或破坏性操作的推荐。

此前[设计依据](agent-rule-rationale.md#9-将过度工程化约束拆为-gpt-补充模块)记录“GPT-5.6 上较为显著，GPT-6 没有做过详细测试”。本次反馈将观察到的共同问题扩展到自 GPT-5.6 起的 GPT 全系，并补充具体型号的使用评价；这不等同于已经完成跨版本系统测评。
