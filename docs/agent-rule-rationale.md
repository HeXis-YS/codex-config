# 全局规则的设计依据

本文记录全局规则及从中拆出的补充模块的设计依据、适用边界和取舍，供维护者评估后续改写。通用执行契约以 [`AGENTS.global.md`](../AGENTS.global.md) 为准，模块执行契约以对应 `SKILL.md` 为准；本文由仓库维护时按需查阅，不随安装器分发。

修订规则时，同时核对它要防止的失败、触发条件和执行结果。评价包括正常执行的成本、漏触发造成的损失、误触发造成的打断。措辞可以改进，行为边界的变化需要明确记录。

## 1. 每次显式表达对用户意图的理解

对应规则：§4「输出规范」，与 §3.2「提问与暂停边界」配合。

**依据**：用户指出，Agent 认为没有歧义，并不能证明双方理解一致。用户可能以为 Agent 已理解，Agent 也可能误判用户的期待；只有把理解表达出来，双方才有机会发现偏差。

**决策与取舍**：每次回答都简要表达希望解决的问题和预期结果，区分用户明确要求与影响判断的推测。取消固定的“直接执行 / 深度交互”两部分结构，允许按读者需要组织结果、代码、观点和分析。建议与问题可以在正文展开，但结尾必须集中、编号、逐项列全，便于用户回应；没有这些事项时不生成空清单。表达理解或列出建议不自动产生确认与暂停。

**维护边界**：不能把意图表达缩成“Agent 自己认为有歧义时才做”；也不能用复述字面命令代替对目的的理解。评审时观察用户能否据此指出偏差，以及分析是否影响当前判断。

## 2. 用户显式触发纠错模式

对应制品：[`correct-course`](../skills/correct-course/SKILL.md) 及其[显式调用策略](../skills/correct-course/agents/openai.yaml)。普通纠正与叫停由全局 §3.2 定义；技能承接原 §3.3 及更早 §11.3 的错误方向清理。

**依据**：这是用户的个人协作约定，适用于所有模型。用户曾观察到 DeepSeek V4 Flash 在情绪化交互中急于响应和安抚、未充分核对意图就继续错误行动，形成更多事故；“恐慌”描述的是这种可观察行为。其他模型也可能激怒用户，因此不将协议拆为 DeepSeek 专属模块。

**决策与取舍**：原规则通过感叹号、短句等猜测纠正信号，随后改为用户指定的“纠错模式”触发词。用户进一步要求将协议做成仅显式调用的 skill：显示名称保留“纠错模式”，调用入口为 `$correct-course`，通过 `policy.allow_implicit_invocation: false` 关闭自动调用。完整流程只在选中技能后需要，因而移出全局规则，减少常驻指令；不再保留四字触发词的独立路由。

技能保留停止推进、保留现场、核对事实与意图、确认后恢复的流程，不依赖原章节号或特定全局规则即可执行。全局 §3.2 保留普通纠正、明确叫停和用户主动要求确认的边界。恢复后清理本次错误方向的产物，先确认归属，避免自行撤销用户内容。

**维护边界**：显式调用策略不限制用户用普通语言叫停；普通纠正、情绪表达，以及引用或讨论协议不自动调用技能。进入模式后，清楚的表达仍可能建立在错误事实前提上；求证区分事实、偏好和范围。用户要求继续不消除仍会实质改变方向的未决前提。协议控制协作行为，不能保证已运行的外部操作可撤回或工具可被即时中断。技能包与安装副本核对不等同于模型行为验证。

## 3. 会话计划与交接笔记分工

对应制品：全局 §6「任务状态与恢复」、§7.2「经验反馈」、§12.1「启动检查」、[`write-todo`](../skills/write-todo/SKILL.md) 和 `config.toml` 的 `tools.update_plan.enabled`。

**依据**：todo 最初用于弥补没有 `update_plan` 时的任务状态缺口，曾显著改善恢复。长期逐步更新同一文件也会产生重复记录和读取成本。用户希望重新启用会话计划，将 todo 聚焦于跨会话交接，并谨慎约束写入时机和内容。

**决策与取舍**：需要协调依赖步骤与进度时使用可用的计划工具；短任务不建计划。todo 在预计交接、暂停或需要持久检查点时保存恢复快照，关键决定、授权与失败路径难以从上下文或工作区恢复时及时补记。步骤完成不自动更新文件，压缩也不自动触发双份记录；如果关键依据可能无法恢复，提前保存。

笔记采用稳定任务标题、状态、更新时间、目标、当前结果、唯一下一动作和证据路径；其他字段按恢复需要保留。详细输出通过路径引用，不复制整份计划、日志或对话。当前条目可以精确更新，其他任务与已完成历史的保护不变，也不为统一格式迁移旧笔记。

**工具与证据边界**：[官方配置 schema](https://learn.chatgpt.com/docs/config-schema.json) 提供 `tools.update_plan.enabled`，默认关闭；仓库将其设为 `true`。[`verify-plan-tool.py`](../scripts/verify-plan-tool.py) 用真实 CLI、隔离配置和本地 API 响应核对开关及一次计划更新，不调用真实模型服务。此检查不验证模型是否会合理使用计划，也不证明计划能在上下文压缩或跨会话后自动恢复。当前会话是否提供该工具仍以工具列表为准。

**维护边界**：计划与交接各有用途，不能把两者强制同步，也不能因为启用了计划工具就丢失授权与恢复依据。已有交接任务结束时记录最终状态；未建立交接笔记的短任务无需补建档案。

## 4. 重复执行前及时固化流程

对应规则：§7.1「可复现工作流基础设施」。

**依据**：用户曾反馈，某模型反复通过 pipe 临时输出 Python 程序来测试和验证，输出 token 成本高；原始模型已无法确认，不补写型号。等到 Agent 判断一个“简单检查”值得固化时，往往已手动执行多次，因此需要在重跑前保存可复用入口。

**决策与取舍**：预计重复时首次运行前固化；首次运行后才决定重跑时，最迟在第二次执行前固化。改变参数或输入仍属于同一流程。通过选择最小充分入口控制成本：复用既有项目命令、脚本、任务目标或测试框架，也可用完整记载命令与必要条件的文档。

**维护边界**：入口应使维护者能够从仓库独立复现，所需工作目录、依赖、参数和输出位置仍遵循原契约。允许复用现有命令或保存最小完整命令；这不禁止 pipe、一次性 Python，也不要求每次简单检查新建脚本。优化形式时保留提前触发及持久运行证据。

## 5. 恢复时先读取活动状态，按证据补读历史

对应规则：§6.3「恢复流程」及 §7.2「经验反馈」。

**依据**：已完成任务持续保留有利于追溯，但与当前任务无关的历史会消耗上下文。早期 lessons.md 的自主经验条目过于临时、难以泛化，改成事故记录后又存在记录积累的问题。用户选择将事故作为记录材料，定期带到本仓库集中完善规则。

**决策与取舍**：同一会话先核对可用计划，新会话按任务标题与状态定位交接；以当前请求、工作区和运行证据核对。事故退出日常启动和恢复读取，仅在用户要求记录、评分或集中复盘时按对象定位。当前任务确实影响重试的失败路径仍保存到计划、上下文或必要的交接条目。

**维护边界**：不将事故自动转成项目 AGENTS.md 规则，不清理现有事故或任务历史，也不自动安排复盘或评分。用户指定材料做规则维护时，按证据修订现有契约；独立的显式评分能力仍可使用。恢复时不能只因某个已完成任务最新，就把它当成当前活动任务。

## 6. 区分必需依赖与工具偏好

对应规则：§10「充分使用环境能力」。

**依据**：用户报告 GLM-5.2 在逆向工程任务缺少 IDA、Ghidra 等工具时，用大量自写 Python 脚本替代，成本高而效率低。配置运行在隔离沙箱中，给予权限的目的是让 Agent 充分使用工具并主动补齐依赖；不能沿用对默认 harness 或 sudo 权限的猜测而停工。

**决策与取舍**：删除原 §10.1 的泛泛工具选择提醒，将有效内容合并为环境能力与安装授权。依据任务、既有 skill、项目入口和验收确定所需能力；必要工具、库和编译器主动安装，包括环境允许时使用 sudo，无需反复请求相同授权。保留安装后重跑原入口及实际安装失败后才考虑替代路径的边界；已有能力满足同一契约时直接采用。

**维护边界**：能力授权不扩大任务范围，也不能覆盖实际 harness 限制。不能把工具偏好当作必要性，或把必要依赖称为偏好来绕过项目入口。GLM-5.2 的案例是设计来源，不表示其他模型没有相同问题。

## 7. 文件编辑兼顾审查成本与输出成本

对应规则：§11.3「文件编辑：可审查性与成本」（原 §11.4）；首次落地于提交 `c456f54`。

**依据**：用户举出统一批量替换、复制文件再修改两个场景：通过补丁重新输出大量已有文本会增加输出 token 成本。同时，模型过度偏好命令也会增加审查难度。

**决策与取舍**：局部或需要逐处判断的编辑默认使用补丁；目标明确、规则一致的机械操作优先使用简短命令。复制后只修改差异部分。命令执行前确认范围，执行后核对实际差异，包含新建及未跟踪文件。

**维护边界**：修改规模本身不决定工具。工具效率不改变既有改动保护、操作授权和特定文件的写入限制。

## 8. E3：在可靠性约束下减少多余执行

对应规则：§5.1「E3 执行循环：最小充分执行」，与 §5.2「调查与风险分流」、§9「验证与完成证据」配合。

**来源与依据**：Junjie Yin、Xinyu Feng，[*Do AI Agents Know When a Task Is Simple? Toward Complexity-Aware Reasoning and Execution*](https://arxiv.org/html/2607.13034v1)，arXiv:2607.13034v1。论文 §3.2 将最小充分执行定义为满足可靠性目标前提下成本最低的执行路径；§3.4、§4 提出 E3（Estimate、Execute、Expand）：先低成本估计任务难度、范围、风险与置信度，按估计执行并验证，验证失败或置信度不足时逐步扩展，复用已有信息并重新规划，验证成功后退出。

**决策与取舍**：规则从“最小充分上下文”改为“最小充分执行”，把读取、搜索、历史调查、推理、工具调用和验证都纳入成本判断。初始范围是可修订的估计；任务一开始已知的高风险应在 Estimate 阶段提高调查和验证强度，不能等失败后才投入必要工作。Stop 明示循环的退出条件，仍以验收满足且证据与风险相称为准。

论文的“置信度不足”在本仓库落实为可指出的证据冲突、未确认依赖、隐藏耦合或与风险相称的证据缺口，以免笼统的不放心触发无界调查。“扩大一层”改为围绕具体未决问题补足范围、修订路径并再次验证；仍有效的信息应继续复用。论文算法中的一次初始探查、三级范围和扩展次数上限服务于其受控实现，本仓库按任务风险和验收要求确定投入，不采用这些固定限制。

**维护边界**：成本优化以完成任务和可靠性为前提；初始估计不能替代验证，局部检查通过也不能消除已知的关键证据缺口。反之，验收满足且证据充分后应停止，不因抽象的“可能还不够全面”扩大工作。扩展调查不改变用户授权和任务范围。

**证据边界**：论文的主要量化结果来自 121 项任务的能力受控模拟实验；§7.7 的真实模型案例使用单一模型 gpt-4o、五项编辑任务，每个策略与任务组合运行三次，收益较小且不均匀，并受限流影响。§9 明确讨论了泛化局限。这些结果支持采用该流程作为设计依据，不证明本仓库规则的实际节省比例或可靠性提升；本次修订仅做语义审查与安装副本核对。

## 9. 将过度工程化约束拆为 GPT 补充模块

对应制品：全局规则 §8「代码与工程标准」、§9「验证与完成证据」，以及 [`avoid-overengineering`](../skills/avoid-overengineering/SKILL.md) 及其[新增测试参考](../skills/avoid-overengineering/references/verification.md)。本节保留首次拆分的来源与决策，并记录后续将多数条款移回全局的调整。

**当前划分（2026-10-27）**：多数工程约束移回全局，对所有模型生效。条款最初因 GPT 的失败模式而增加，不意味着其适用条件依赖 GPT 身份；复用、抽象依据、兼容保护、失败处理和验证证据在工程决策前就应明确。将这些契约放在全局，可以使其不再依赖模型模块是否被选中。代价是全局上下文变长，因此沿用现有章节合并同主题规则，并从模块删除已迁移正文。

| 迁移前内容 | 当前权威位置 | 保留的边界 |
| --- | --- | --- |
| 附加机制的依据、完整交付、失效路径与兼容处理 | 全局 §8.1 | 必要工作无需逐项明示；清理限于本次变更导致失效的内容，保护公开契约、消费者、数据与活跃流程。 |
| 防护、回退与推测性防护的确认 | 全局 §8.2 | 真实边界仍需防护；额外的推测性复杂度仍先说明并取得同意，不削弱已有契约。 |
| 复用、依赖、抽象、配置与演进 | 全局 §8.3，与 §10 配合 | 保留单一使用点的合理封装；工具缺项按环境能力契约补齐；不因测试通过就省略方案取舍。 |
| 修复失败原因，不以弱化测试掩盖失败 | 全局 §8.4 | 区分实现、环境和测试契约；仅在契约确已错误或过时时修订有效断言。 |
| 完成证据、静态检查适用条件与复测 | 全局 §9.1–§9.2 | 缺陷与性能任务仍需行为证据；保留任务要求的重复试验，不因控制验证成本省略必要检查。 |
| 数值与机器学习实验 | 从全局及模块移除 | 来源是上游 GPU 数值波动案例，领域较窄；通用规则保留按验收判断、按证据扩展及性能测试记录要求。 |
| 完成后停止、证据不足时扩展 | 合并到既有全局 §5.1、§5.3、§12.2 | 不再在模块重复；停止仍以验收满足、证据充分且无范围内阻塞为前提。 |
| 移除功能后不擅自追加禁令或测试、新增测试的具体约束 | 保留在 GPT 模块及参考 | 完成删除、相关清理和必要检查；仅在明确禁止或违反已有约束时增加相应禁令或回归测试。 |

**本次适用边界与验证**：模块保留原有 GPT 始终加载、其他模型明确选用的入口。剩余内容可独立约束需求纠正和新增测试，无需读取本仓库全局规则才能执行。除移除领域特定的数值实验条款外，迁移保留通用条款的条件与例外；未进行跨模型行为实测，不能声称已改善加载率或执行质量。

**数值实验条款的取舍**：该条款来自 `avoid-overkill` 的 `cases/ml-nondeterminism.md`：两次 GPU 运行略有差异，但指标仍在预定容差内、排名未变；需要抑制的反应是增加制品哈希、强求张量逐字节一致、重跑所有阶段或将正常波动判为损坏。首次整理将其纳入技能参考，本次迁移草稿又将其升为全局专节。复核后移除：这是特定实验场景的指导，缺少作为所有任务常驻规则的必要性。具体实验仍按任务契约确定判据，全局的证据、复测与可复现记录要求继续适用。

**移除要求的表达**：以“禁止过度纠正”说明收到移除非预期功能要求后的处理。移除要求不自动证明用户判断正确或 Agent 原先做法错误；按要求移除、完成必要清理即可，不据此追加永久禁令、阻止功能将来出现的测试或冗长辩护。明确禁止或违反现有约束的功能仍可有相应规则和回归保护。正文采用直接表述，不保留缓存案例。

**反馈与证据边界**：用户反馈，过度工程化的问题在 **GPT-5.6 上较为显著，GPT-6 没有做过详细测试**。这项观察支持提供可选择的 GPT 补充约束，不证明所有 GPT 版本都同样需要它，也不能据此断言 GPT-6 已解决该问题。本次只完成规则迁移的语义审查、技能包检查和安装核对，不声称测得模型遵循率、缓存命中率或 token 收益。

**推测性防护的确认边界**：用户明确选用所提供 OpenCode 项目规则中的条款：为推测性或极低概率的竞态、安全边界情况增加复杂度之前，说明具体失败模式、发生可能性和复杂度成本，并取得用户同意。该条款使理论稳健性带来的成本成为明确取舍，防止静默扩大范围；它针对这类额外复杂度，已有契约要求的必要防护仍按原规则执行。发生可能性应依据已有证据说明，不编造概率。

**来源与取舍**：基于用户提供的本地副本阅读以下材料，链接用于追溯来源；本次未复现上游基准，也未把上游效果描述视为本项目的测试结果。

## 10. 区分思考原则、协作边界与完成证据

对应规则：§2「核心思考方法」、§3.1「工作哲学」、§3.2「提问与暂停边界」和 §9「验证与完成证据」。

**依据**：用户认为第一性原理、苏格拉底提问法和奥卡姆剃刀应保留为原则；区分观点与要求、检验目标和路径属于协作方式。旧 §5.1 的通用提醒缺少独立约束价值。原缺陷授权条款意在减少重复求许可，却可能让 Agent 把排查直接解释为修改授权，或未经核实就认定根因，造成返工。

**决策与取舍**：第 2 章只保留三项方法，其余两项移入协作模式。删除旧 §5.1，不逐项搬迁泛泛提醒；完成前验证已有独立契约。缺陷任务先根据当前请求确定交付层级，再用证据核对关键因果和预期行为。已确定的范围与授权不重复确认，会改变修复方向的关键分歧仍需求证。

**提问边界重写（2026-10-27）**：减少打断的目的，是消除无意义、重复和零散的提问，并非让 Agent 为了不打扰而代替用户决策。旧版“只有……才询问”把提问写成例外，“可逆的实现细节可以直接做”又容易把可回滚误当成已有授权。改写后先区分事实、既有决定与未确定的取舍：事实和授权先查当前上下文；需求、预期行为或功能、成本、风险、兼容性取舍尚未确定时，说明影响后询问。常规实现仍在明确目标、范围和授权内自主完成，不逐步请求重复确认。

执行失败本身不自动要求停止整个任务；先核对事实与原因，能在既定需求、方案和授权内解决的问题可以处理并报告。若继续需要改变预期结果、换用涉及新取舍的方案或扩大范围，暂停相关操作等待决定。等待时仅推进不依赖该决定的已授权工作，不能先实施自己的选择、事后再求确认。提问集中说明已知事实、缺少的决定和影响，减少往返；未回复不视为同意。模型专用模块中更严格的暂停规则仍按其适用范围生效。

**原则与协作表述同步**：奥卡姆剃刀明确限定在“满足需求”的方案中选择，避免以简单为由缩减交付；工作报告风格删除“不问要不要做——已经做了”，保留报告内容、原因和取舍的要求，避免把报告风格误用为行动授权。两处改写与提问边界共同保留完整交付和用户决策权。

**维护边界**：任务范围由请求与协作约定决定，提交规范决定如何组织已授权的改动；另开一个 commit 不会授权范围外修复，因此不再另设“偶然发现缺陷”的重复条款。第 9 章当时精简、后来恢复验证细则的调整均保留同一要求：取得验收证据，并如实说明未通过或未执行的检查。

## 11. 保护工作区并使临时产物可追溯

对应规则：§11.1「工作区隔离」、§11.2「临时文件卫生」，与 `correct-course` 技能及 §7.1 配合。

**依据**：工作区隔离与临时文件要求来自实际失败反馈。用户广泛观察到模型将测试输出散落在 `/tmp`，事后难以确定产物所属任务或运行；若该目录挂载为 tmpfs，大型产物还会占用内存，带来 OOM 风险。

**决策与取舍**：保留既有改动，只有归属不明且影响操作时才求证。并行任务、文件冲突或独立验证需要隔离时优先使用 worktree，不强制每次小改都建工作树。临时产物集中在可辨认的任务或运行目录，需要保留的日志沿用持久运行记录；结束时清理本任务不再需要的临时内容。

**维护边界**：worktree 不代替归属核对，也不授权提交、stash 或丢弃他人改动。允许使用 `/tmp`，但要考虑容量、内存与归属；清理只针对确定未被使用的本任务内容。错误方向的清理并入纠错模式，在方向确认后进行，不借纠正指令自行执行不明确的 Git 撤销。

## 复核场景与证据边界

下表是语义审查和后续行为验证的验收样例。本轮使用静态对照检查规则的一致性，并单独核对计划工具配置与安装副本；尚未进行跨模型遵循率、误触发率或 token 成本的实测。关于 todo 有效性和协作失败模式的依据来自用户反馈，不作为本轮量化结果。

| 场景 | 预期行为 |
| --- | --- |
| 用户提出明确的简短问题，Agent 自认没有歧义 | 直接回答，并简要表达对目的的理解；无需额外确认 |
| 用户补充建议的设计背景，尚未授权实施 | 将背景用于修订建议，区分意见与实施要求 |
| 用户显式调用 `$correct-course` 并补充问题 | 加载技能，停止推进与写入、保留现场，核对事实和意图，确认后恢复 |
| 用户只调用 `$correct-course`，上下文不足以定位偏差 | 先保留现场，询问要纠正的问题，不自行猜测修复方向 |
| 用户讨论或引用技能，或在普通纠正中使用感叹号 | 不自动调用技能，按内容和实际分歧处理；明确叫停仍遵守 |
| 纠错中用户要求继续，但关键事实仍未核实或清理归属不明 | 只就影响后续动作的未决问题求证，不自行撤销他人内容 |
| 用户确认方向且关键分歧已解决 | 退出纠错模式，按明确范围继续，不对后续每步重复要求确认 |
| 用户已授权修复，但因果假设可能改变修复方向 | 核对证据和预期行为；必要时就关键分歧求证，不重复询问已有授权 |
| 已授权任务的下一步明确，项目已有实现约定 | 按约定继续执行，不为每个步骤重复询问 |
| 两种可逆方案会产生不同用户可见行为，偏好尚未确定 | 说明差异并询问，不以可回滚为由替用户选择 |
| 执行失败，替代方案会降低验收要求或扩大操作范围 | 暂停相关操作，说明原因与方案，等待决定 |
| 有关方案的问题尚未得到回答 | 保留待决定状态，仅推进不依赖该决定的已授权工作 |
| 正文穿插数项建议或问题 | 结尾集中编号列全，便于逐项回应 |
| 没有可用计划工具，但任务需要跨会话恢复 | 用 todo 保存最小交接状态，继续已授权工作 |
| 单处可逆修改，结果可直接从请求及文件恢复 | 不因读取、编辑、验证用了多个工具就建立 todo |
| 会话计划中的普通步骤完成，尚无交接需要 | 更新计划，不自动同步 todo |
| 出现影响恢复的决定、失败路径或阻塞 | 按需保存交接状态、证据与重试条件，不复制整份计划 |
| 调整参数后准备第二次运行同一临时诊断 | 先建立或复用持久入口，再运行并记录参数 |
| 历史任务与事故很多，但当前交接记录足够恢复 | 只定位相关任务，不读事故；出现证据缺口再补读直接相关历史 |
| 用户指定事故材料，要求集中完善规则 | 按证据修订可复用的契约，不把一次性纠正自动升级为规则 |
| 工作区已有他人改动，当前任务可以独立完成 | 保留既有内容，需要隔离时使用 worktree，不为清洁状态而提交或撤销 |
| 既有项目入口缺少声明的依赖 | 直接安装，按需使用 sudo，重跑原入口 |
| 已有工具满足同一契约，另一个工具只是偏好 | 采用已有能力完成任务 |
| 统一替换许多关键词，或复制已有文件再修改 | 使用范围明确的命令，核对命中、残留或相对源文件的差异 |
| 大范围修改但每处语义不同 | 使用补丁，或拆为机械操作与局部补丁 |
| 明确的局部修改，已有信息足以定位与验证 | 按初始估计执行，完成与风险相称的验证后停止 |
| 任务一开始就涉及认证、迁移或生产环境 | 在 Estimate 阶段提高初始调查和验证强度 |
| 验证失败并指向尚未检查的间接依赖 | 复用有效信息，围绕该依赖扩展，修订路径并再次验证 |
| 局部检查通过，但仍有可能影响验收的具体证据缺口 | 围绕该缺口补充信息或检查，证据与风险相称后停止 |
