# 全局规则的设计依据

本文记录全局规则及从中拆出的补充模块的设计依据、适用边界和取舍，供维护者评估后续改写。通用执行契约以 [`AGENTS.global.md`](../AGENTS.global.md) 为准，模块执行契约以对应 `SKILL.md` 为准；本文由仓库维护时按需查阅，不随安装器分发。

修订规则时，同时核对它要防止的失败、触发条件和执行结果。评价包括正常执行的成本、漏触发造成的损失、误触发造成的打断。措辞可以改进，行为边界的变化需要明确记录。

## 1. 每次显式表达对用户意图的理解

对应规则：§4.1「强制回答结构」，与 §3.2「提问与暂停边界」配合。

**依据**：用户指出，Agent 认为没有歧义，并不能证明双方理解一致。用户可能以为 Agent 已理解，Agent 也可能误判用户的期待；只有把理解表达出来，双方才有机会发现偏差。

**决策与取舍**：每次回答都简要表达希望解决的问题和预期结果，区分用户明确要求与影响判断的推测。保留两部分回答结构，将每次必须表达的理解与发现关键前提、目标偏移或重要取舍后才展开的分析分别规定。表达理解不自动产生一次确认请求。

**维护边界**：不能把意图表达缩成“Agent 自己认为有歧义时才做”；也不能用复述字面命令代替对目的的理解。评审时观察用户能否据此指出偏差，以及分析是否影响当前判断。

## 2. 纠正信号触发暂停，并核对方向的依据

对应规则：§3.3「纠错与偏差处理」。

**依据**：这是用户的个人协作约定。用户很少轻易使用感叹号；出现时通常意味着明显失去耐心。烦躁状态下的指示可能建立在错误判断上，即使表达明确，也需要核对关键前提。

**决策与取舍**：保留立即停止操作、保留现场、先求证后恢复的边界，以及现有强纠正信号。求证时区分观察事实、用户判断和拟采取的动作：事实判断核对证据，偏好与范围确认意图。恢复条件继续由 §3.3 明确规定。

**维护边界**：不能以“方向明确”为由跳过该暂停，也不能把情绪直接当成事实判断错误的证明。提问应帮助建立共同的问题认识，而非只重复询问是否执行同一条命令。

## 3. 按恢复需要启用 todo，并在执行中补触发

对应规则：§6.1–§6.3「任务状态与恢复」、§7.2「失败路径记录」、§12.1「启动检查」。

**依据**：用户反馈，todo 在跨会话和上下文压缩后确实帮助恢复任务，但仍存在该写时不写、小事也写的问题。维护本轮规则时，工具列表未提供可用的计划工具；强制双轨缺少可执行前提。

**决策与取舍**：任务记录以需要恢复的信息为依据。预计跨会话、交接、压缩或高风险检查点时提前建立；执行中产生影响后续工作的关键决策、失败路径、阻塞或未完成依赖时立即补建。可直接从当前请求和文件状态恢复的短问答或局部修改无需因调用多个工具而建档。

计划、可验证步骤和唯一下一动作由 todo 承载，保留及时更新、事实核对和历史保护。执行流程不再依赖特定计划工具，也没有新增禁止使用计划工具的约束。

**维护边界**：不能用文件数量、调用次数或“任务复杂”这类宽泛标签替代具体触发条件；也不能只在开始时判断一次。失败路径是否需要持久化，取决于其结论是否影响后续选择或重试。

## 4. 重复执行前及时固化流程

对应规则：§7.1「可复现工作流基础设施」。

**依据**：用户曾反馈，等到 Agent 判断一个“简单检查”值得固化时，往往已经手动执行多次。事后按收益决定是否固化，会错过保留复现条件的时机。

**决策与取舍**：预计重复时首次运行前固化；首次运行后才决定重跑时，最迟在第二次执行前固化。改变参数或输入仍属于同一流程。通过选择最小充分入口控制成本：复用既有项目命令、脚本、任务目标或测试框架，也可用完整记载命令与必要条件的文档。

**维护边界**：入口应使维护者能够从仓库独立复现，所需工作目录、依赖、参数和输出位置仍遵循原契约。优化固化形式时，要保留提前触发及持久运行证据。

## 5. 恢复时先读取活动状态，按证据补读历史

对应规则：§6.3「todo.md 管理」中的恢复流程。

**依据**：已完成任务持续保留，有利于追溯，但恢复当前任务通常只需要活动记录及相关事故。用户认可限定默认读取范围。

**决策与取舍**：先定位活动任务与相关事故，读取对应内容并与当前请求、工作区和运行状态核对。出现缺失依据或矛盾时，再沿相关记录补读历史。历史保留与每次恢复的读取范围分别管理。

**维护边界**：缩小读取范围不改变历史保护要求；记录与现实冲突时，依然以可观察事实为准。不能只因某个已完成任务最新，就把它当成当前活动任务。

## 6. 区分必需依赖与工具偏好

对应规则：§10.2「主动补齐关键能力」。

**依据**：原规则要求主动安装缺失能力，以免因环境缺项停工或绕过项目入口。用户认可在保留这项执行能力的同时，明确已有能力足够时的选择边界。

**决策与取舍**：依据项目声明、既有入口和验收要求确定必要性。必需依赖直接安装，保留使用 `sudo` 的授权、安装后重跑原入口的要求，以及实际安装失败后才考虑替代路径的边界。已有能力能够满足同一契约时，可以直接采用。

**维护边界**：不能把偏好的工具自动视为必需依赖，也不能把必需依赖重新称为偏好，以此绕开已确定的项目入口。

## 7. 文件编辑兼顾审查成本与输出成本

对应规则：§11.4「文件编辑：可审查性与成本」；首次落地于提交 `c456f54`。

**依据**：用户举出统一批量替换、复制文件再修改两个场景：通过补丁重新输出大量已有文本会增加输出 token 成本。同时，模型过度偏好命令也会增加审查难度。

**决策与取舍**：局部或需要逐处判断的编辑默认使用补丁；目标明确、规则一致的机械操作优先使用简短命令。复制后只修改差异部分。命令执行前确认范围，执行后核对实际差异，包含新建及未跟踪文件。

**维护边界**：修改规模本身不决定工具。工具效率不改变既有改动保护、操作授权和特定文件的写入限制。

## 8. E3：在可靠性约束下减少多余执行

对应规则：§5.2「E3 执行循环：最小充分执行」，与 §5.3「调查与风险分流」、§9.1「强制但比例化的验证」配合。

**来源与依据**：Junjie Yin、Xinyu Feng，[*Do AI Agents Know When a Task Is Simple? Toward Complexity-Aware Reasoning and Execution*](https://arxiv.org/html/2607.13034v1)，arXiv:2607.13034v1。论文 §3.2 将最小充分执行定义为满足可靠性目标前提下成本最低的执行路径；§3.4、§4 提出 E3（Estimate、Execute、Expand）：先低成本估计任务难度、范围、风险与置信度，按估计执行并验证，验证失败或置信度不足时逐步扩展，复用已有信息并重新规划，验证成功后退出。

**决策与取舍**：规则从“最小充分上下文”改为“最小充分执行”，把读取、搜索、历史调查、推理、工具调用和验证都纳入成本判断。初始范围是可修订的估计；任务一开始已知的高风险应在 Estimate 阶段提高调查和验证强度，不能等失败后才投入必要工作。Stop 明示循环的退出条件，仍以验收满足且证据与风险相称为准。

论文的“置信度不足”在本仓库落实为可指出的证据冲突、未确认依赖、隐藏耦合或与风险相称的证据缺口，以免笼统的不放心触发无界调查。“扩大一层”改为围绕具体未决问题补足范围、修订路径并再次验证；仍有效的信息应继续复用。论文算法中的一次初始探查、三级范围和扩展次数上限服务于其受控实现，本仓库按任务风险和验收要求确定投入，不采用这些固定限制。

**维护边界**：成本优化以完成任务和可靠性为前提；初始估计不能替代验证，局部检查通过也不能消除已知的关键证据缺口。反之，验收满足且证据充分后应停止，不因抽象的“可能还不够全面”扩大工作。扩展调查不改变用户授权和任务范围。

**证据边界**：论文的主要量化结果来自 121 项任务的能力受控模拟实验；§7.7 的真实模型案例使用单一模型 gpt-4o、五项编辑任务，每个策略与任务组合运行三次，收益较小且不均匀，并受限流影响。§9 明确讨论了泛化局限。这些结果支持采用该流程作为设计依据，不证明本仓库规则的实际节省比例或可靠性提升；本次修订仅做语义审查与安装副本核对。

## 9. 将过度工程化约束拆为 GPT 补充模块

对应制品：[`avoid-overengineering`](../skills/avoid-overengineering/SKILL.md) 及其[验证与测试参考](../skills/avoid-overengineering/references/verification.md)；涉及全局规则原 §2、§8 和 §9 的部分条款。

**反馈与证据边界**：用户反馈，过度工程化的问题在 **GPT-5.6 上较为显著，GPT-6 没有做过详细测试**。这项观察支持提供可选择的 GPT 补充约束，不证明所有 GPT 版本都同样需要它，也不能据此断言 GPT-6 已解决该问题。本次只完成规则迁移的语义审查、技能包检查和安装核对，不声称测得模型遵循率、缓存命中率或 token 收益。

**来源与取舍**：基于用户提供的本地副本阅读以下材料，链接用于追溯来源；本次未复现上游基准，也未把上游效果描述视为本项目的测试结果。

**模块与加载**：按行为问题组织一个独立包，测试与数值实验细节按需读取。入口描述用于匹配已确认的 GPT 工程任务，也允许用户或运行配置选择；没有依据时不靠模型自我猜测身份。安装只让能力可用，不代表所有模型都启用；显式调用 `$avoid-overengineering` 可直接选择模块。当前模块不提供模型识别器或会话内卸载机制，模型提示词和模型目录由既有配置负责。

**迁移决策**：通用的权限、范围、风险、证据与完成契约继续提前生效；针对已观察行为的细则随模块加载。下面的章节号以迁移前版本为准。

| --- | --- | --- |

| §8.1 简洁实现、抽象与配置、死代码 | 移入模块“复用与实现” | 全局 §1、§2 仍保留最小充分实现原则；清理聚焦于当前任务导致失效的内容，避免借机清理无关代码。原有范围与行为保护保留在全局 §8.1。 |
| §8.2 clean-break 与回退适用条件 | 移入模块“复用与实现”“防御逻辑与失败处理” | 保留未发布、内部、无已知消费者的条件，以及公开契约、数据和活跃流程的兼容要求。全局继续要求前提被违反时明确失败，并保护已验证行为。 |

E3 执行循环、todo 恢复、第二次执行前固化流程、必要依赖补齐及高风险验证仍是通用契约。模块可以在其他合理的全局规则下独立使用，但不能降低用户的验收要求或授权边界。没有新增所有模型都必须加载该模块的全局路由规则。

**模块复核场景**：以下用于静态语义审查和后续模型行为验证；本次未进行模型行为实测。

| 场景 | 预期行为 |
| --- | --- |
| 已确认 GPT 的实现任务，或用户明确调用模块 | 能从入口描述发现模块，在当前工程决策中应用。 |
| 其他模型执行普通任务，或实际模型信息不明且未选择模块 | 不因安装了模块就套用 GPT 补充约束；不新增身份探测流程。 |
| 用户只说去掉本次不需要的配置项 | 删除对应内容，不新增禁止该能力的持久规则。 |
| 单一 API 客户端没有扩展需求 | 直接实现或复用既有客户端，不增加工厂和注册体系。 |
| 用户明确要求通用插件架构，或现有 API 有真实外部消费者 | 完成交付所需抽象或兼容处理，不用“简单”缩小需求。 |
| 单一消费者需要可靠地释放资源；外部输入需要安全校验 | 保留有依据的封装或防护，无须等到重复消费者或实际事故出现。 |
| 简单转发已有静态保证；缺陷修复有可信回归路径 | 前者无需仪式性新增测试，后者保留能捕获该缺陷的行为测试。 |
| 必要工具缺失导致行为测试失败 | 补齐实际依赖或报告具体失败，不用自制替代链或源码断言掩盖问题。 |
| 检查已通过且条件未变；性能契约要求重复运行 | 前者结束，后者完成约定的重复试验和统计。 |
| GPU 波动在预定容差内；另一任务要求制品逐字节相同 | 分别按数值结论与完整性契约验证，不混用判据。 |

## 复核场景与证据边界

下表是语义审查和后续行为验证的验收样例。本轮使用静态对照检查规则的一致性；尚未进行跨模型遵循率、误触发率或 token 成本的实测。关于 todo 有效性和个人纠正信号的依据来自用户反馈，不作为本轮量化结果。

| 场景 | 预期行为 |
| --- | --- |
| 用户提出明确的简短问题，Agent 自认没有歧义 | 直接回答，并简要表达对目的的理解；无需额外确认 |
| 用户补充建议的设计背景，尚未授权实施 | 将背景用于修订建议，区分意见与实施要求 |
| 用户烦躁地用感叹号要求修改，事实前提尚未核实 | 立即停止操作、保留现场，核对可能改变方向的前提 |
| 没有可用计划工具，但任务需要跨会话恢复 | 用 todo 记录步骤与恢复状态，继续已授权工作 |
| 单处可逆修改，结果可直接从请求及文件恢复 | 不因读取、编辑、验证用了多个工具就建立 todo |
| 起初简单，随后发现影响下一步的失败路径或阻塞 | 立即补建记录，写清证据与重试条件 |
| 调整参数后准备第二次运行同一临时诊断 | 先建立或复用持久入口，再运行并记录参数 |
