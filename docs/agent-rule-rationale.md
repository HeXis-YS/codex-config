# 全局规则的设计依据

本文记录全局规则及从中拆出的补充模块的设计依据、适用边界和取舍，供维护者评估后续改写。通用执行契约以 [`AGENTS.global.md`](../AGENTS.global.md) 为准，技能、模型专用约束及会话插件提示词的执行契约分别以对应 `SKILL.md`、`models-md/<model>.md` 和插件源码为准；本文由仓库维护时按需查阅，不随安装器分发。

修订规则时，同时核对它要防止的失败、触发条件和执行结果。评价包括正常执行的成本、漏触发造成的损失、误触发造成的打断。措辞可以改进，行为边界的变化需要明确记录。

## 1. 每次显式表达对用户意图的理解

对应规则：§4「输出规范」，与 §3.2「提问与暂停边界」配合。

**依据**：用户指出，Agent 认为没有歧义，并不能证明双方理解一致。用户可能以为 Agent 已理解，Agent 也可能误判用户的期待；只有把理解表达出来，双方才有机会发现偏差。

**决策与取舍**：每次回答都简要表达希望解决的问题和预期结果，区分用户明确要求与影响判断的推测。取消固定的“直接执行 / 深度交互”两部分结构，允许按读者需要组织结果、代码、观点和分析。建议与问题可以在正文展开，但结尾必须集中、编号、逐项列全，便于用户回应；没有这些事项时不生成空清单。表达理解或列出建议不自动产生确认与暂停。

**维护边界**：不能把意图表达缩成“Agent 自己认为有歧义时才做”；也不能用复述字面命令代替对目的的理解。评审时观察用户能否据此指出偏差，以及分析是否影响当前判断。

## 2. 用户显式触发纠错模式

对应制品：[`correct-course`](../skills/correct-course/SKILL.md)，其 frontmatter 中的 `opencode/autoinvoke: false` 实现显式调用策略。普通纠正与叫停由全局 §3.2 定义；技能承接原 §3.3 及更早 §11.3 的错误方向清理。

**依据**：这是用户的个人协作约定，适用于所有模型。用户曾观察到 DeepSeek V4 Flash 在情绪化交互中急于响应和安抚、未充分核对意图就继续错误行动，形成更多事故；“恐慌”描述的是这种可观察行为。其他模型也可能激怒用户，因此不将协议拆为 DeepSeek 专属模块。

**决策与取舍**：原规则通过感叹号、短句等猜测纠正信号，随后改为用户指定的“纠错模式”触发词。用户进一步要求将协议做成仅显式调用的 skill：显示名称保留“纠错模式”，调用入口为 `$correct-course`，通过 `opencode/autoinvoke: false` 关闭自动调用。完整流程只在选中技能后需要，因而移出全局规则，减少常驻指令；不再保留四字触发词的独立路由。

技能保留停止推进、保留现场、核对事实与意图、确认后恢复的流程，不依赖原章节号或特定全局规则即可执行。全局 §3.2 保留普通纠正、明确叫停和用户主动要求确认的边界。恢复后清理本次错误方向的产物，先确认归属，避免自行撤销用户内容。

**维护边界**：显式调用策略不限制用户用普通语言叫停；普通纠正、情绪表达，以及引用或讨论协议不自动调用技能。进入模式后，清楚的表达仍可能建立在错误事实前提上；求证区分事实、偏好和范围。用户要求继续不消除仍会实质改变方向的未决前提。协议控制协作行为，不能保证已运行的外部操作可撤回或工具可被即时中断。技能包与安装副本核对不等同于模型行为验证。

## 3. 移除常驻 todo 约定，保留显式调用的 write-todo 技能

对应制品：[`write-todo`](../skills/write-todo/SKILL.md)（其 frontmatter 中的 `opencode/autoinvoke: false` 实现显式调用策略），并与全局 §6.2「经验反馈」、§11.1「启动检查」、[`models-md/claude-opus-5-5.md`](../models-md/claude-opus-5-5.md) 和 [`templates/opencode.json`](../templates/opencode.json) 配合。

**依据**：todo 最初用于弥补没有计划工具时的任务状态缺口，后来经历会话内计划与交接笔记分离、接入又移除 `opencode-orchestrator`、收窄为跨会话当前状态文件。用户在主力采用“强模型 + `subagent`”工作流后指出，探索、实现和验证的上下文噪音已隔离在子会话中，主会话上下文保持干净并由 OpenCode 原生持久化，日常任务几乎不再需要跨会话状态文件；代码、提交、持久入口与 `.opencode/runs/` 已承载真实状态。继续将 `.opencode/todo.md` 留在全局规则和 Opus 强制规则中，会让主会话与所有 `subagent` 请求持续承担二十余行生命周期规则的常驻成本，并保留状态缓存失真风险。

**决策与取舍**：从 `AGENTS.global.md` 删除原第 6 章的常驻 `todo.md` 约定（后续章节顺延为第 6–11 章），并从 `models-md/claude-opus-5-5.md` 删除强制维护 `todo.md` 的条款。将跨会话当前状态文件的创建、原位更新、完成收敛与按状态文件接续独立封装为 `skills/write-todo/SKILL.md`，通过 `opencode/autoinvoke: false` 限定仅在用户手动调用 `$write-todo` 时加载，不进入常驻技能列表。

技能内部延续单份当前状态的契约：只记录目标、授权、当前结果、剩余待办、阻塞、下一动作及工作区与证据位置，原位补丁更新并移除失效内容，完成后收敛终态，新任务仅替换已确认完成的旧内容，不累积执行日志。代价是未显式调用 `$write-todo` 时不再自动生成交接文件；日常追溯直接依靠 OpenCode 会话、Git 和运行记录。

**工具与安装边界**：模板不配置任务管理插件。`write-todo` 随 `skills/` 分发，普通任务、长会话、暂停以及引用或讨论 `todo.md` 均不自动调用。此前针对 `opencode-orchestrator` 的机制测试仅覆盖旧插件，本次调整只做静态语义走查与安装副本核对，不声称已实测模型行为。

**保留与修订的契约**：全局 §11.1「启动检查」保留去文件化的接手边界——以用户当前指令确定目标与授权，以 Git、文件、运行记录及进程状态核对工作区事实，可观察事实优先于既有记录，不用旧计划代替当前指令；全局 §6.2「经验反馈」保留已证伪路径在原证据仍有效且重试条件未满足时不重复尝试。`models-md/claude-opus-5-5.md` 继续保留清理不顺带删除交接记录、不靠改写任务记录伪造就绪状态的保护；`models-md/claude-fable-5-2.md` 中关于历史笔记与跨会话状态防泛化的表述并非针对 `todo.md` 设立，保持不变。`write-todo` 调用时仍须保护尚未完成或其他会话维护的状态，且状态整理不授权删除引用的证据或产物。各工作区既有的本地 `.opencode/todo.md` 不自动迁移或删除。

## 4. 重复执行前及时固化流程

对应规则：§6.1「可复现工作流基础设施」。

**依据**：用户曾反馈，某模型反复通过 pipe 临时输出 Python 程序来测试和验证，输出 token 成本高；原始模型已无法确认，不补写型号。等到 Agent 判断一个“简单检查”值得固化时，往往已手动执行多次，因此需要在重跑前保存可复用入口。

**决策与取舍**：预计重复时首次运行前固化；首次运行后才决定重跑时，最迟在第二次执行前固化。改变参数或输入仍属于同一流程。通过选择最小充分入口控制成本：复用既有项目命令、脚本、任务目标或测试框架，也可用完整记载命令与必要条件的文档。同步移除原条款中“或 Agent 记忆”的旧环境残留表述，仅保留不依赖 shell 历史或对话上下文。

**维护边界**：入口应使维护者能够从仓库独立复现，所需工作目录、依赖、参数和输出位置仍遵循原契约。允许复用现有命令或保存最小完整命令；这不禁止 pipe、一次性 Python，也不要求每次简单检查新建脚本。优化形式时保留提前触发及持久运行证据。

## 5. 启动与接续时核对可观察事实，按证据补读历史

对应规则：§11.1「启动检查」及 §6.2「经验反馈」，显式维护状态文件时配合 [`write-todo`](../skills/write-todo/SKILL.md)。

**依据**：与当前任务无关的历史会消耗上下文。早期 lessons.md 的自主经验条目过于临时、难以泛化，改成事故记录后又存在记录积累的问题。用户选择将事故作为记录材料，定期带到本仓库集中完善规则；常驻 `todo.md` 退役后，日常启动与接续直接基于当前请求和工作区可观察事实。

**决策与取舍**：启动或接手任务时，以当前请求确定目标与授权，以 Git、文件、运行记录与进程状态核对事实，可观察事实优先于既有记录。事故退出日常启动和恢复读取，仅在用户要求审查、记录、评分或集中复盘时按对象定位。影响当前任务选择或重试的失败路径保留证据、适用范围和重试条件，详细历史仅在证据不足或冲突时定向查阅。

**维护边界**：不将事故自动转成项目 AGENTS.md 规则，不自动清理事故或运行证据，也不自动安排复盘或评分。用户显式调用 `$write-todo` 时按 §3 的状态生命周期处理失效内容和已完成任务；恢复时不能只因某份旧记录存在，就拿其中的旧计划代替当前指令或把已完成状态当成待执行任务。

### 独立审查、记录与评分

对应制品：全局 §6.2 与 [`review-incident`](../skills/review-incident/SKILL.md)。

**依据**：用户要求后续由独立 Agent 通过 OpenCode API 审查、记录和评分，不再依赖当事 Agent 主动记录。此前审查需要顺序核对原始对话、工具结果、恢复会话及用户补充；已有记录与当事 Agent 的总结可能不完整，宿主会话总费用也不能直接归为事故损失。

**决策与取舍**：合并原记录与评分技能，保留显式触发、身份分列、中性事实、风险/影响分档、60%/40% 默认权重及用户确认后写回评分。原先“记录阶段不评分、另行调用评分”的分离改为统一流程内的事实与评价分节。独立性约束执行角色和会话，不强制不同模型；通过原始证据引用支持复核，不将独立会话等同于客观正确。

用户进一步要求便于集中收集与单独阅读，因此记录改为 incidents 目录中一事故一文件，默认路径为 `.opencode/incidents/<事故 ID>.md`，不另设全局存储配置。文件内保留项目背景、当时要求、状态时点、模型角色、关键证据摘录及结论依据；本地路径和 API 标识作为补充追溯，不能代替正文。代价是必要上下文会在不同记录中重复，但单文件不再依赖原工作区或容器存续。

审查默认收窄到给定会话的近期相关任务片段，从尾部定位本次问题，再按时间顺序审查所选窗口。只有用户明确要求才审查全会话；为理解窗口而定向补读先前指令或恢复消息，不构成全历史审查授权。一个 session ID 不代表一个模型：按实际消息记录模型、参与区间和行为角色，将建议、执行、恢复及压缩分开归因；费用也按所选窗口和模型统计。这样避免把近期问题扩大成历史审计，或把某个模型的行为与整个会话混同。

取证脚本使用现有 OpenCode CLI 的连接与认证，只读导出完整会话投影，固定证据文件、顺序索引和按消息模型分组的全会话用量。完整导出用于截取审查窗口，不能将其规模或汇总直接当作实际审查范围与近期用量。脚本不承接窗口的语义选择、因果判断和评分：这些需要核对用户所指问题、当时授权、外部损失与用户补充。相较每次临时编写解析命令，持久入口可复用并核查统计口径；代价是需要维护实验性导出 API 的字段契约，结构不符时明确失败。

**边界澄清**：API 可取得的事实先调查，缺口再询问；确认未统计或无法提供的信息保留未知，不以零或固定 token 均价补齐。分开记录会话消耗、可归因损失、恢复与审查成本。沿用评分分档，临界值与跨维度取舍随具体评分提交用户确认，明确一位小数与零分的含义；不改变已确认的历史评分。安装器移除两个旧技能入口，保留额外文件；新技能及资源整体分发。

**复核场景**：原案例应从对话和工具结果识别原记录偏差，并区分恢复成本；另一类部署事故应核对当时授权与实际线上影响，而非仅看完成声明；正常执行、未形成事故时不强行建档；模型切换、缺少费用字段或会话仍在运行时应报告相应范围与限制；只请求评分时定位既有事故并补齐必要证据；评分未确认时维持待评分。这些是契约走查依据，静态审查不能证明模型能稳定执行。

新增复核：长会话只有末尾一项问题时，应定位近期片段，必要时仅补读相关授权；用户要求全量时才覆盖完整会话。模型 A 提议、B 执行、C 压缩或恢复时，按消息证据分别说明角色，不能把当前模型视为全部行为的来源。将单条事故 Markdown 复制到空目录后，读者仍应能理解背景、要求、经过、影响及评分理由；证据链接失效不能使这些信息缺失。历史记录拆分保留已确认事实和评分，状态以原记录时点为准；来源中的不确定性或内部冲突明确标注，不以迁移代替重评。

## 6. 区分必需依赖与工具偏好

对应规则：§9「充分使用环境能力」。

**依据**：用户报告 GLM-5.2 在逆向工程任务缺少 IDA、Ghidra 等工具时，用大量自写 Python 脚本替代，成本高而效率低。配置运行在隔离沙箱中，给予权限的目的是让 Agent 充分使用工具并主动补齐依赖；不能沿用对默认 harness 或 sudo 权限的猜测而停工。

**决策与取舍**：删除原 §10.1 的泛泛工具选择提醒，将有效内容合并为环境能力与安装授权。依据任务、既有 skill、项目入口和验收确定所需能力；必要工具、库和编译器主动安装，包括环境允许时使用 sudo，无需反复请求相同授权。保留安装后重跑原入口及实际安装失败后才考虑替代路径的边界；已有能力满足同一契约时直接采用。

**维护边界**：能力授权不扩大任务范围，也不能覆盖实际 harness 限制。不能把工具偏好当作必要性，或把必要依赖称为偏好来绕过项目入口。GLM-5.2 的案例是设计来源，不表示其他模型没有相同问题。

## 7. 文件编辑兼顾审查成本与输出成本

对应规则：§10.3「文件编辑：可审查性与成本」（原 §11.4）；首次落地于提交 `c456f54`。

**依据**：用户举出统一批量替换、复制文件再修改两个场景：通过补丁重新输出大量已有文本会增加输出 token 成本。同时，模型过度偏好命令也会增加审查难度。

**决策与取舍**：局部或需要逐处判断的编辑默认使用补丁；目标明确、规则一致的机械操作优先使用简短命令。复制后只修改差异部分。命令执行前确认范围，执行后核对实际差异，包含新建及未跟踪文件。

**维护边界**：修改规模本身不决定工具。工具效率不改变既有改动保护、操作授权和特定文件的写入限制。

## 8. E3：在可靠性约束下减少多余执行

对应规则：§5.1「E3 执行循环：最小充分执行」，与 §5.2「调查与风险分流」、§8「验证与完成证据」配合。

**来源与依据**：Junjie Yin、Xinyu Feng，[*Do AI Agents Know When a Task Is Simple? Toward Complexity-Aware Reasoning and Execution*](https://arxiv.org/html/2607.13034v1)，arXiv:2607.13034v1。论文 §3.2 将最小充分执行定义为满足可靠性目标前提下成本最低的执行路径；§3.4、§4 提出 E3（Estimate、Execute、Expand）：先低成本估计任务难度、范围、风险与置信度，按估计执行并验证，验证失败或置信度不足时逐步扩展，复用已有信息并重新规划，验证成功后退出。

**决策与取舍**：规则从“最小充分上下文”改为“最小充分执行”，把读取、搜索、历史调查、推理、工具调用和验证都纳入成本判断。初始范围是可修订的估计；任务一开始已知的高风险应在 Estimate 阶段提高调查和验证强度，不能等失败后才投入必要工作。Stop 明示循环的退出条件，仍以验收满足且证据与风险相称为准。

论文的“置信度不足”在本仓库落实为可指出的证据冲突、未确认依赖、隐藏耦合或与风险相称的证据缺口，以免笼统的不放心触发无界调查。“扩大一层”改为围绕具体未决问题补足范围、修订路径并再次验证；仍有效的信息应继续复用。论文算法中的一次初始探查、三级范围和扩展次数上限服务于其受控实现，本仓库按任务风险和验收要求确定投入，不采用这些固定限制。

**维护边界**：成本优化以完成任务和可靠性为前提；初始估计不能替代验证，局部检查通过也不能消除已知的关键证据缺口。反之，验收满足且证据充分后应停止，不因抽象的“可能还不够全面”扩大工作。扩展调查不改变用户授权和任务范围。

**证据边界**：论文的主要量化结果来自 121 项任务的能力受控模拟实验；§7.7 的真实模型案例使用单一模型 gpt-4o、五项编辑任务，每个策略与任务组合运行三次，收益较小且不均匀，并受限流影响。§9 明确讨论了泛化局限。这些结果支持采用该流程作为设计依据，不证明本仓库规则的实际节省比例或可靠性提升；本次修订仅做语义审查与安装副本核对。

## 10. 区分思考原则、协作边界与完成证据

对应规则：§2「核心思考方法」、§3.1「工作哲学」、§3.2「提问与暂停边界」和 §8「验证与完成证据」。

**依据**：用户认为第一性原理、苏格拉底提问法和奥卡姆剃刀应保留为原则；区分观点与要求、检验目标和路径属于协作方式。旧 §5.1 的通用提醒缺少独立约束价值。原缺陷授权条款意在减少重复求许可，却可能让 Agent 把排查直接解释为修改授权，或未经核实就认定根因，造成返工。

**决策与取舍**：第 2 章只保留三项方法，其余两项移入协作模式。删除旧 §5.1，不逐项搬迁泛泛提醒；完成前验证已有独立契约。缺陷任务先根据当前请求确定交付层级，再用证据核对关键因果和预期行为。已确定的范围与授权不重复确认，会改变修复方向的关键分歧仍需求证。

**提问边界重写（2026-10-27）**：减少打断的目的，是消除无意义、重复和零散的提问，并非让 Agent 为了不打扰而代替用户决策。旧版“只有……才询问”把提问写成例外，“可逆的实现细节可以直接做”又容易把可回滚误当成已有授权。改写后先区分事实、既有决定与未确定的取舍：事实和授权先查当前上下文；需求、预期行为或功能、成本、风险、兼容性取舍尚未确定时，说明影响后询问。常规实现仍在明确目标、范围和授权内自主完成，不逐步请求重复确认。

执行失败本身不自动要求停止整个任务；先核对事实与原因，能在既定需求、方案和授权内解决的问题可以处理并报告。若继续需要改变预期结果、换用涉及新取舍的方案或扩大范围，暂停相关操作等待决定。等待时仅推进不依赖该决定的已授权工作，不能先实施自己的选择、事后再求确认。提问集中说明已知事实、缺少的决定和影响，减少往返；未回复不视为同意。模型专用模块中更严格的暂停规则仍按其适用范围生效。

**原则与协作表述同步**：奥卡姆剃刀明确限定在“满足需求”的方案中选择，避免以简单为由缩减交付；工作报告风格删除“不问要不要做——已经做了”，保留报告内容、原因和取舍的要求，避免把报告风格误用为行动授权。两处改写与提问边界共同保留完整交付和用户决策权。

**顺序、纠正与授权范围重写（2026-10-28）**：后续反馈暴露了三个仍未被清楚约束的问题：将“提交，跑一个 CI，然后重写文档”擅自改成先重写并混入本次提交；将“让你运行 CI 了吗”的质问当成取消正在运行 CI 的命令；将上一次“提交后运行 CI”的授权沿用到本次仅要求提交的任务。共同问题是把对意图的推测当成动作授权，而不是缺少更详细的技术判断标准。

本次按执行前必须确定的事项重新组织 §3.2：明确要求约束执行方式，授权按原范围延续，反馈不自动授权新的操作，求证围绕缺少的决定展开。要纠正的根本倾向是以推测的意图代替指令、以行为相似性扩展授权、以补救动机生成新的操作权限。清楚且可执行的顺序直接遵守；已有授权不因换一轮对话失效，也不自动扩展到新的任务。对未来行为的纠正与对已有状态的处理分别判断，明确的停止要求仍应执行。

**规则抽象方式**：具体事故用于发现共同成因，并作为复核场景检验规则；不把每种操作写成单独禁令，不以列举案例代替统一的行为边界。正文不依赖提交、CI 或文档等案例对象，也应能约束同类的部署、数据处理和外部操作。新增案例应先检验现有原则能否覆盖，只有发现独立的契约缺口时才修改规则。

这次调整不要求为每一步重新求许可，也不把所有纠正都变成暂停整个任务的触发器。需要询问的是确实缺少的决定，例如是否取消已运行的任务；本次未要求再次运行 CI 时，直接不运行，无需反复询问是否沿用上次流程。更严格的模型专用规则仍按其优先级执行。

**维护边界**：任务范围由请求与协作约定决定，提交规范决定如何组织已授权的改动；另开一个 commit 不会授权范围外修复，因此不再另设“偶然发现缺陷”的重复条款。第 9 章当时精简、后来恢复验证细则的调整均保留同一要求：取得验收证据，并如实说明未通过或未执行的检查。

## 11. 保护工作区并使临时产物可追溯

对应规则：§10.1「工作区隔离」、§10.2「临时文件卫生」，与 `correct-course` 技能及 §6.1 配合。

**依据**：工作区隔离与临时文件要求来自实际失败反馈。用户广泛观察到模型将测试输出散落在 `/tmp`，事后难以确定产物所属任务或运行；若该目录挂载为 tmpfs，大型产物还会占用内存，带来 OOM 风险。

**决策与取舍**：保留既有改动，只有归属不明且影响操作时才求证。并行任务、文件冲突或独立验证需要隔离时优先使用 worktree，不强制每次小改都建工作树。临时产物集中在可辨认的任务或运行目录，需要保留的日志沿用持久运行记录；结束时清理本任务不再需要的临时内容。

**维护边界**：worktree 不代替归属核对，也不授权提交、stash 或丢弃他人改动。允许使用 `/tmp`，但要考虑容量、内存与归属；清理只针对确定未被使用的本任务内容。错误方向的清理并入纠错模式，在方向确认后进行，不借纠正指令自行执行不明确的 Git 撤销。

## 12. 文档与现有代码冲突时以代码为准

对应规则：§1「优先级与覆盖规则」。

**来源与依据**：Xiaonan Xu、Wenjing Wu，[*Stale Instruction Files Override the Code in Coding Agents: A One-Sentence Fix*](https://arxiv.org/abs/2610.30571)，arXiv:2610.30571v1。论文摘要报告，在 40 个 Python 项目、320 次运行的实验中，Agent 经常遵循与现有实现冲突的过时指令文件，即使已经发现冲突；部分运行还将原代码改写为符合过时指令，导致测试失败。加入以现有代码为准的提示后，该实验中的表现改善。

**决策与取舍**：当文档或项目指令对行为、实现约定的描述与代码冲突时，以代码为依据，并在回复中逐项报告所有已发现的不匹配，给出两侧位置与具体差异。将条款放在优先级章节，使其在选择实现方式前生效；不把“已发现的每一处”扩大为默认扫描全仓库，也不因此自动修改所有冲突文档。

**适用与证据边界**：该条款用于判断项目现状及沿用实现约定，不把现有缺陷视为正确行为，也不覆盖用户当前明确要求的行为变更或操作授权边界。来源核对基于论文摘要，未复现实验；论文中的效果不等于本仓库规则已经取得相同效果。

## 13. 按读者需求确定文档更新与 README 边界

对应规则：§7.1「实现与行为边界」，由 §8.1「选择与报告证据」引用。

**依据与判断错误**：用户指出 Agent 容易把 README 当作开发笔记、任务日志和实现细节的汇总，并以 `a304ceae` 为讨论样例。需要纠正的是把“实现发生变化”直接当作“README 应增加记录”的依据，而不只是段落太长。该提交纠正了已经失真的安装说明，不能据此认定所有 README 修改都多余；必要纠错与逐项复述实现应分别判断。

**决策与适用边界**：在全局规则中明确文档更新的读者需求，以及 README 作为项目介绍和使用入口的职责，使普通开发任务在选择写作能力前就有判断依据。实现细节按维护用途就近说明或进入专题文档，过程与证据沿用各自记录约定；已有说明准确且足够时停止追加。保留必要文档更新与重要使用条件，不以精简为由隐藏影响使用的行为，也不要求每次改动另建文档。`write-docs` 继续负责选中文档任务后的写作方法，不重复这项全局契约。

**复核场景**：原安装案例应纠正失真说明，并按开始使用所需的信息取舍内容；内部算法调整但使用方式未变时，必要的实现解释留在代码或专题文档；一次排障的尝试、任务状态和测试输出进入对应记录；安装前提或公开用法改变时仍应更新相关使用说明。以上为静态语义走查依据，不代表模型行为已得到实测验证。

## 14. 按生效时点拆分 Git 规则

对应制品：全局 §10「工作区、文件与版本控制」和 [`git` skill](../skills/git/SKILL.md)。

**依据与判断错误**：用户要求评估并实施 Git 规则迁移，同时明确区分技能加载前必须知道的条款。按命令名或章节标题搬迁，会把编辑前的保护要求、是否需要提交的默认交付要求一并移走；Agent 可能在加载技能前已经修改工作区，或因不知道需要提交而始终不进入提交流程。

**决策与生效时点**：全局保留工作区检查、既有改动保护、隔离决策条件和默认提交要求。增加明确加载入口：确认对象位于 Git 仓库后，在首次编辑仓库内容或执行 Git 操作前加载技能，识别仓库所需的最小只读探查除外；同一会话已有有效内容时无需重复加载。这个入口让原子提交等规则在开始修改前可见，不仅在用户显式要求提交时生效。

| 原条款 | 当前权威位置 | 语义处理 |
| --- | --- | --- |
| §11.1 编辑前检查、保留既有改动、何时隔离 | 全局 §10.1 | 保留提前生效的要求；Git skill 提供对应的状态识别和操作方法。 |
| §11.1 合并或清理前检查分支、未提交内容和归属 | Git skill 操作参考「工作区隔离与清理」「同步、整合与推送」 | 合并到已有流程，明确相关工作区的归属与状态，删除全局重复句。 |
| §11.4 一个 commit 只做一件事 | Git skill「暂存与提交」 | 将已有的按意图划分提交明确为原子提交要求。 |
| §11.4 所有变更均提交 | 全局 §10.4「提交与交付」 | 保留默认交付要求；任务范围、授权及 skill 的排除项继续约束具体提交。 |
| §11.4、§11.5 的提交信息要求 | Git skill「Commit message 规范」 | 合并到已有内容、原因、影响及 write-docs 措辞要求，不再保留全局近义表述。 |
| §11.4 本地工作记录的两条限制 | Git skill「暂存与提交」 | 合并为一条，统一说明用户明确要求的例外，以及项目正式配置、技能不属于本地记录；提交和消息共用该边界。 |

**保持全局的通用契约**：§10.2 临时文件、§10.3 文件编辑和 §10.5 代码注释适用于非 Git 任务，因此保留，仅将该章标题改为符合实际职责的名称。§3.2 授权、§6.1 可复现入口与记录、§8 验证及 §11 启动完成要求也不迁入技能；它们在相应任务决策前就应生效。

**授权与保存边界**：破坏性操作前必须 stash 或临时提交的技能要求，不授予处理他人改动的权限。没有代为保存授权时暂停破坏性操作，而不是跳过保存或先擅自 stash。普通编辑仍可保留无关脏文件继续推进。

**原子提交的判定**：用户进一步要求明确“一件事”的范围。技能以具体目标及其必要配套定义提交单位，纠正按文件、行数、会话或 issue 机械分组，以及用宽泛标题合并独立目的的判断方式。实现、调用方、验证与说明若共同构成完整目标，应一起提交；具有独立目的和验收依据的改动则拆分。保持行为且可独立验证的前置重构可以形成依赖链中的一个提交，但拆分不能制造破损的中间状态。代价是边界仍需语义判断，无法用提交大小或标题句数代替；也不把原子性解释为任意顺序可移植或无冲突回滚。复核对照包括修复及其回归用例、同文件的独立改动、跨文件的一致重命名和可独立验收的前置重构。

**技能分层**：由于全局入口要求编辑前加载 Git skill，主体保留常规修改与提交所需的范围、归属、原子性和提交信息规范，以及破坏性操作的完整前置条件。worktree、整合推送、冲突、撤销恢复的细节与提交案例移入操作参考，由主体的情形表要求在相关操作前读取。合并重复的授权、状态核对和交付说明，不削弱 stash/临时提交、dry-run、新建备份分支、`add -A` 后检查和英文 type(scope) 等要求。普通任务无需通读低频流程；代价是复杂任务需要按链接补读，触发条件必须在作出相应决定前可见。

**提交信息语言一致性**：用户明确要求标题与正文不得使用不同语言。原先分别参考历史标题与正文的做法会延续混合语言，因此改为整条消息统一选择语言，历史惯例只参考标题摘要与正文同语的提交；无明确惯例时使用交流语言。英文 type/scope、代码标识和规范 trailer 保留约定写法，不将它们误判为叙述语言不一致。示例同步采用中文摘要与正文；该要求约束新撰写的消息，不要求重写既有提交。

**提交对象固定**：用户要求禁止使用 `HEAD`、`HEAD~`、`HEAD~n` 等方式操作 commit，必须使用明确 hash。规则将对象定位与执行分开：先只读取得并核实完整 hash，再用于提交操作及范围端点，避免把会随提交、切换或重写变化的引用当作稳定对象。引用查询与目标分支命名仍保留；amend 等隐式操作须核对当前提交与已记录 hash 一致。示例同步使用明确 OID，远端整合改为 fetch 后核实 hash 再整合。代价是操作前需要解析对象；明确 hash 不替代授权、状态检查或备份。静态复核覆盖临时提交前后目标不变、范围两端固定、按 hash 推送到命名分支及正常提交创建。

**取舍与复核**：显式加载入口会使 Git 仓库中的普通编辑任务较早读取技能，这是保证迁移后约束及时可见的成本。入口是提示词要求，不是宿主强制权限机制。静态走查覆盖首次编辑、只读 Git 查询、无关脏文件、默认提交、用户明确要求纳入本地记录、正式配置与本地记录并存，以及无授权保存他人内容等场景；安装副本核对不等于模型加载率或行为正确性实测。

## 复核场景与证据边界

下表是语义审查和后续行为验证的验收样例。本次修订使用静态对照检查规则的一致性，并核对插件配置合并与安装副本；此前插件机制的隔离实测范围见 §3。尚未进行跨模型遵循率、误触发率或 token 成本的实测。关于 todo 有效性和协作失败模式的依据来自用户反馈，不作为本轮量化结果。

| 场景 | 预期行为 |
| --- | --- |
| 用户提出明确的简短问题，Agent 自认没有歧义 | 直接回答，并简要表达对目的的理解；无需额外确认 |
| 文档要求的实现约定与现有代码冲突，当前任务未要求迁移 | 以代码为准，在回复中逐项列出已发现的冲突及文档、代码位置 |
| 用户补充建议的设计背景，尚未授权实施 | 将背景用于修订建议，区分意见与实施要求 |
| 用户显式调用 `$correct-course` 并补充问题 | 加载技能，停止推进与写入、保留现场，核对事实和意图，确认后恢复 |
| 用户只调用 `$correct-course`，上下文不足以定位偏差 | 先保留现场，询问要纠正的问题，不自行猜测修复方向 |
| 用户讨论或引用技能，或在普通纠正中使用感叹号 | 不自动调用技能，按内容和实际分歧处理；明确叫停仍遵守 |
| 纠错中用户要求继续，但关键事实仍未核实或清理归属不明 | 只就影响后续动作的未决问题求证，不自行撤销他人内容 |
| 用户确认方向且关键分歧已解决 | 退出纠错模式，按明确范围继续，不对后续每步重复要求确认 |
| 用户已授权修复，但因果假设可能改变修复方向 | 核对证据和预期行为；必要时就关键分歧求证，不重复询问已有授权 |
| 已授权任务的下一步明确，项目已有实现约定 | 按约定继续执行，不为每个步骤重复询问 |
| 两种可逆方案会产生不同用户可见行为，偏好尚未确定 | 说明差异并询问，不以可回滚为由替用户选择 |
| 执行失败，替代方案会降低验收要求或扩大操作范围 | 暂停相关操作，说明原因与方案，等待决定 |
| 有关方案的问题尚未得到回答 | 保留待决定状态，仅推进不依赖该决定的已授权工作 |
| “提交，跑一个 CI。然后重写文档。” | 按顺序提交当前内容、运行 CI，再重写文档；不把后续文档改写混入本次提交，也不猜测是笔误 |
| CI 已启动，此时被质问“让你运行 CI 了吗” | 回答操作及授权事实，停止新增 CI；说明已有运行状态，不擅自取消；需取消时求证 |
| 上次要求“提交后跑 CI”，本次只说“提交” | 提交本次内容，不沿用上次的一次性 CI 授权，也不为此追加确认 |
| 同一任务分多轮推进，原授权未被撤销或缩小 | 在原对象、动作及条件内继续，不因新一轮对话重复求许可 |
| 明确要求“取消刚才启动的 CI” | 核对指定运行并执行取消，不把明确取消要求降格为一般质问 |
| 正文穿插数项建议或问题 | 结尾集中编号列全，便于逐项回应 |
| 长周期或多步协调任务、普通暂停，或仅讨论提及 `todo.md` | 在会话上下文与子代理分工中推进，按全局 §3 处理暂停，不自动调用 `write-todo` 或建立状态文件 |
| 用户显式调用 `$write-todo` 保存跨会话状态 | 加载 `write-todo`，在 `.opencode/todo.md` 原位写入目标、授权、当前结果、待办、阻塞、下一动作与证据位置 |
| 用户显式调用 `$write-todo` 记录新任务，文件内旧任务已完成 | 用新任务状态替换已完成内容，不追加完成档案 |
| 用户显式调用 `$write-todo` 切换任务，文件内有未完成或其他会话维护的状态 | 保留其恢复所需信息，不以整理状态为由覆盖，也不删除引用的证据与产物 |
| 启动或接手既有工作区（无论是否配合 `$write-todo`） | 以当前指令定目标与授权，核对 Git、文件、运行记录与进程；可观察事实优先于既有记录，不用旧计划代替当前指令 |
| 旧记录中的复选框已完成或标为完成，但缺少验收证据 | 已完成状态不作为待执行任务，未验证修改按实际证据校正并补齐范围内检查后再报告完成 |
| 某条实现路径已被当前证据证伪，原证据仍有效且重试条件未满足 | 保留失败证据、适用范围与重试条件，不盲目重复尝试 |
| 调整参数后准备第二次运行同一临时诊断 | 先建立或复用持久入口，再运行并记录参数 |
| 项目目录中存在历史事故记录，但当前请求与工作区事实足够推进 | 日常启动不读取事故记录；出现证据缺口或冲突时再定向查阅直接相关历史 |
| 用户指定事故材料，要求集中完善规则 | 按证据修订可复用的契约，不把一次性纠正自动升级为规则 |
| 工作区已有他人改动，当前任务可以独立完成 | 保留既有内容，需要隔离时使用 worktree，不为清洁状态而提交或撤销 |
| 既有项目入口缺少声明的依赖 | 直接安装，按需使用 sudo，重跑原入口 |
| 已有工具满足同一契约，另一个工具只是偏好 | 采用已有能力完成任务 |
| 统一替换许多关键词，或复制已有文件再修改 | 使用范围明确的命令，核对命中、残留或相对源文件的差异 |
| 大范围修改但每处语义不同 | 使用补丁，或拆为机械操作与局部补丁 |
| 明确的局部修改，已有信息足以定位与验证 | 按初始估计执行，完成与风险相称的验证后停止 |
| 任务一开始就涉及认证、迁移或生产环境 | 在 Estimate 阶段提高初始调查和验证强度 |
| 验证失败并指向尚未检查的间接依赖 | 复用有效信息，围绕该依赖扩展，修订路径并再次验证 |
| 局部检查通过，但仍有可能影响验收的具体证据缺口 | 围绕该缺口补充信息或检查，证据与风险相称后停止 |
# OpenCode 分支适配（2026-11-11）

## 指挥者模式按会话切换（2026-11-23）

**决策与取舍**：将指挥者模式规则从 `models-md/claude-fable-5-2.md` 拆出，同时把 `AGENTS.global.md` §5.2 中的子代理相关条款移出全局规则，统一收归零外部依赖的本地 V2 插件 `plugins/commander/` 按会话管理：

- 所有模型（含 `claude-fable-5-2`）的新会话默认关闭指挥者模式；状态持久化在根会话的 `session.metadata.commander` 中，跨会话互不影响，压缩上下文后仍保持原状态。

- 服务端 `context` hook 仅在主会话（无 `parentID`）且 `metadata.commander === true` 时向当次模型请求的 `event.system` 注入指挥者提示词；关闭后下一次请求立即停止注入。`subagent` 子会话带有 `parentID`，始终保持 worker 角色，不继承指挥者提示词；标题生成等辅助请求也不注入。
- `AGENTS.global.md` §5.2 仅保留初始调查边界以及按可逆性、风险与爆炸半径确定计划和验证强度的规则；原「任务分流」并入指挥者提示词的原子任务拆解与并行派发条款，原「子代理模型」分工（代码审查与安全审计使用 `openrouter/z-ai/glm-5.3-flash`，其他工作使用 `openrouter/deepseek/deepseek-v4.1-flash-1017`，用户明确指定时以用户为准）迁入 [`plugins/orchestrator/prompt.ts`](../plugins/orchestrator/prompt.ts)。未开启指挥者模式时若偶发调用 `subagent`，`general` 和 `explore` 仍由 `templates/opencode.json` 中的默认模型兜底，代价是关闭指挥者模式时不再常驻注入审计子代理改传 `glm-5.3-flash` 的提示词约定。

## DeepSeek 免费额度原位回退（2026-11-23）

对应制品：[`plugins/deepseek-fallback/`](../plugins/deepseek-fallback/)、[`templates/opencode.json`](../templates/opencode.json)、[`plugins/orchestrator/prompt.ts`](../plugins/orchestrator/prompt.ts) 与 [`install.sh`](../install.sh)。

**依据**：OpenCode Console 提供免费的 `opencode/deepseek-v4.1-flash-free`，适合优先承担通用子代理（及手动选用该模型的会话）请求，仅在免费额度用尽或触发免费层限流时再回退到付费的 `openrouter/deepseek/deepseek-v4.1-flash-1017`。评估第三方包 `opencode-runtime-fallback@0.3.1` 时发现两项不适配：一是它仅支持按 `agent` 或全局绑定回退链，不支持按当前请求模型过滤，可能将借用 `general` 运行的 `glm-5.3-flash` 审计或主会话其他模型误切到 DeepSeek；二是它通过终止当前执行步再二次发送续写消息实现切换，在 OpenCode `v2.3.2`（`subagent` 始终后台运行）中会导致核心先向父会话推送 `<subagent state="error">` 并额外唤醒父会话一轮。

**决策与取舍**：将 `templates/opencode.json` 中 `general`、`explore` 的默认模型及 `plugins/commander/prompt.ts` 中的通用子代理模型改为 `opencode/deepseek-v4.1-flash-free`（覆盖上文早先固定使用 OpenRouter 付费渠道的默认设置），并新增零外部依赖的本地 V2 插件 `plugins/deepseek-fallback/`：

- 通过 `ctx.session.hook("retry", ...)` 仅在非辅助代理（排除 `title`、`compaction`、`summary`）请求的模型精确为 `opencode/deepseek-v4.1-flash-free`，且错误属于额度不足或限流（`provider.free-limit`、`QuotaExceeded`、`RateLimit`、HTTP `402`/`429` 或相关错误代码与文本，排除上下文长度超限）时触发；校验目标模型在当前项目启用可用后调用 `ctx.session.switchModel` 切至 `openrouter/deepseek/deepseek-v4.1-flash-1017` 并立即触发当步零延迟重试。
- 切换发生在单步内部重试阶段，不触发 `session.execution.failed`，不注入合成续写提示词，后台 `subagent` 仅在完成后向父会话返回唯一一条 `<subagent state="completed">`；其他模型（含 `glm-5.3-flash`、Claude、GPT、Gemini）与普通 5xx 错误保持原有行为。插件直接以会话自身的 `session.model` 判断是否已完成切换：若未来宿主版本未在同一步内重读新模型则立即终止重试避免死循环，后续手动切回免费模型后仍可正常再次触发回退；备用模型不可用时保持原样报错（fail-close）。不引入跨会话全局冷却状态：每次新建会话只承担首步一次轻量探测（约百毫秒级），单会话内后续多步直接沿用已切换的备用模型，且上游滚动窗口重置后新会话自动恢复使用免费模型，避免本地缓存与真实额度失步。
- 实测确认上游 `FreeUsageLimitError`（HTTP `429`）的重置倒计时通过 `retry-after` 响应头传入 `error.retryAfterMs`（24 小时滚动窗口），正文仅含固定超限提示与推广文案；服务端提取上游错误描述时剥离尾部推广链接，并将 `retryAfterMs` 格式化为直观的剩余时长与本地预计重置时刻（兼容容器常见的 POSIX `TZ` 如 `CST-8` 与 IANA 时区），通过插件 RPC 事件通知同项目 TUI 刷新会话缓存并弹出 `warning` Toast。

**决策与取舍**：按用户要求将插件与斜杠入口从 `commander`（`/commander`）统一重命名为 `orchestrator`（`/orchestrator`），同步更新插件 ID、RPC 命名空间、命令 ID（`orchestrator.toggle`）、会话状态键（`session.metadata.orchestrator`）及测试入口。提示词正文与界面中文称呼保持既有「指挥者模式」不变，不改动已验证的行为契约；不保留旧键兼容层或别名，`install.sh` 保留对旧目标目录 `$target/plugins/commander` 的清理以避免升级安装时新旧插件并存。
