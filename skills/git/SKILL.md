# 使用 Git

让目标变更进入正确的历史，同时保留范围外的内容和状态。先确认当前状态与目标差异，再选择影响范围最小、语义明确的操作；工作区干净不是独立目标。

## 范围与状态

- 按当前请求和有效约定区分查询、修改、提交、整合、发布与丢弃。分析不授权修改，提交不自动包含推送、历史重写或清理；授权明确时直接推进，缺少会改变结果的决定时暂停相关操作并询问。
- 进入或切换仓库后，确认根目录、分支或 detached HEAD、工作区和 index 差异，以及进行中的操作。可用 `git rev-parse --show-toplevel`、`git status --short --branch`，按需读取 `git diff`、`git diff --cached` 和未跟踪文件；普通 diff 不包含未跟踪内容。
- **提交定位**：以已有 commit 为操作对象、来源或范围端点时，必须使用已核实的完整 commit hash（OID），禁止使用 `HEAD`、`HEAD~`、`HEAD~n`、`HEAD^` 等相对或符号引用，也不以分支名、标签或 reflog 序号代替。先只读查询并记录 hash，再用于检查与执行；范围两端均须明确。分支名仍可标识要更新的引用。amend 等隐式作用于当前提交的操作，执行前必须核对当前提交与已记录 hash 一致。
- 依据任务、初始状态和编辑证据判断归属。保留无关修改及他人的暂存状态；同文件混合修改按差异块处理，归属不明且影响操作时询问，不用整文件覆盖或清空 index 省略归属判断。
- 变更引用、历史或 index 前核对状态仍有效；出现并行修改、位置切换或失败时复查相关状态，不逐命令重复全仓扫描。未知的 merge/rebase 等中间状态先确认归属，不自行继续或终止。
- CLI、MCP 和宿主工具都须核对实际影响：工作区、index、引用、远端，以及 hooks、过滤器、自动 stash/abort 等行为。工具缺少必要能力时报告限制，不换工具绕过授权。

## 破坏性操作的执行前置条件

适用于 `clean`、`reset`，以及丢弃修改、重写历史、删除引用或工作区的操作，包括丢弃内容的 restore/checkout、amend/rebase、强推和分支/worktree 删除；不以有无 force 参数判断。

1. **检查并保存**：检查相关工作区、index 和未跟踪文件。有未提交改动必须先 stash 或创建临时提交，核对保存内容、记录恢复位置并复查状态；复制文件或创建分支不能替代。保存他人或归属不明的内容缺少授权时暂停询问。
2. **dry-run**：有原生 dry-run 必须使用，目标、路径和过滤选项与正式操作一致；没有则用等效只读检查列明受影响的引用、提交、暂存内容和文件。实际阅读结果，无法确定影响时停止。
3. **新建备份分支**：每次操作前为受影响的提交端点分别新建唯一命名的分支并核对 OID；只影响当前工作区时至少用当前提交的完整 hash 建立备份。已有引用、reflog、stash、临时提交或已推送状态均不能替代。临时提交改变当前提交时，用保存前记录的 OID 保持原操作目标。
4. **补齐并核对**：分支只保存提交历史；受影响但 stash/临时提交未覆盖的暂存版本、未跟踪、忽略或子模块内容及恢复依据须另行保存并核对。临时保存不混入正式交付。授权覆盖实际影响且保存、预检和备份成功后才执行；任何失败或无可备份提交时停止并报告。状态变化后重新检查并补齐保存与备份。

保护步骤不授予额外操作或删除备份的权限。

## 暂存与提交

除非用户明确要求，否则不得将 `.opencode/` 下的本地工作记录提交到 Git 或在 commit message 中提及。项目显式管理的 OpenCode 配置与技能不属于本地工作记录。

1. 按下节及项目约定划定原子提交，检查候选差异及已有暂存内容。整文件属于本次提交时按显式路径暂存；混合修改按差异块暂存。
2. **`git add -A` 后必须用 `git diff --cached --name-status` 检查完整 staged 文件列表**，逐项核对路径、增删与范围，不能直接 commit。所有提交还须检查最终 `git diff --cached` 的内容、新增、删除和模式；显式 add 不排除已有暂存内容，`add -u` 也不按任务筛选。
3. 验证实际提交内容。部分暂存的快照可能不同于测试过的工作区；差异影响结论时验证候选快照，不擅自移走他人修改。
4. 按「Commit message 规范」撰写消息，以非交互方式提交。失败后先确认有无新提交、hooks 是否改动文件及失败原因；不自行跳过检查或修改全局配置。amend 须有历史重写授权，并核实提交归属与发布情况。

### 一件事的范围

一个 commit 对应一个具体、可独立解释、审查和验收的完整目标。暂存前说明目标，并区分目标本身、必要配套和独立改动：

- 缺少便使实现、契约或验收不完整的调用方、配置、迁移、测试及文档，随目标提交；不为凑类别新增工作。
- 各有目的和验收依据、移除一项后另一项仍完整成立的改动应拆分；文件数、行数、type、会话、issue 或宽泛标题都不决定边界。
- 有独立目的、保持行为且可单独验证的前置重构可先提交；内部步骤不机械拆分。每个正式提交须自洽并满足适用的构建与验证要求，不能留下破损接口或刻意分开修复及必要测试。依赖按顺序说明，不承诺任意顺序 cherry-pick 或无冲突 revert。

与目标无必要关系的差异移出当前候选范围；拆分不扩大授权。

### Commit message 规范

- **措辞**：撰写前加载并遵循 [`write-docs`](../write-docs/SKILL.md) 的对应语言和技术报告要求，保留事实、条件与证据限制；单独安装时须同时提供该技能。格式与语言选择按本节。
- **格式**：无用户或项目的其他明确要求时，使用 Conventional Commits：`type(scope): 摘要`，无明确模块时省略 scope。type 选 `feat`、`fix`、`docs`、`refactor`、`perf`、`test`、`build`、`ci`、`chore` 或 `revert`。标题单行，与正文空一行；不照搬历史中的随意格式。
- **语言**：**标题摘要与正文必须使用同一种语言，type 和 scope 必须为英文**。整条消息统一选择语言：优先遵循用户要求，其次项目明确约定，否则参考近期标题摘要与正文同语的代表性提交；无明确惯例时用交流语言。代码标识和规范 trailer 保持原写法。
- **内容**：标题概括具体目标，不写空泛“更新”或文件列表，也不以一句话合并独立意图。正文说明内容、原因、影响及必要的兼容性变化和取舍；短改动可用一段，不重复标题。按需写实际验证与限制，不把计划或推测写成结果。
- **附注**：不兼容变更用 `!` 或 `BREAKING CHANGE:`，说明影响和必要迁移；issue、签署、协作者 trailer 须有真实依据。消息不混入无关操作日志或凭据。

## 核对与交付

核对提交内容与分支、整合或推送的实际目标引用、恢复或清理的结果，以及应保留的内容和剩余状态。无关脏文件可以保留；命令成功或工作区干净不代替验收，本地提交也不等于推送。网络结果不确定时先查询远端。

报告完成的动作、提交或分支、验证与接续状态，满足目标后停止。
