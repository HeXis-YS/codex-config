# 使用 Git

让目标变更进入正确的历史，同时保留范围外的内容和状态。先确认当前状态与目标差异，再选择影响范围最小、语义明确的操作；工作区干净不是独立目标。

## 确定目标与执行范围

- 区分查询、修改、提交、整合、发布和丢弃。依据当前请求和仍有效的约定执行；分析请求不自动授权修改，提交也不自动包含推送、重写历史或清理分支。
- 对授权明确的动作直接推进，不因轮次变化重复确认。目标分支、保留内容或历史处理方式尚未确定且会改变结果时，暂停依赖该决定的操作，集中询问缺少的决定。
- 判断一次操作的影响时，同时考虑工作区、暂存区、引用与提交历史、远端，以及 hooks 或过滤器。命令名字、“本地操作”或“工具调用成功”都不能单独证明它符合目标。
- CLI、MCP 和宿主工具均按实际接口选择。先核对会影响结果的差异，例如提交是否包含整个暂存区、是否运行 hooks、是否自动 stash、冲突后是否自动 abort；工具缺少必要能力时报告限制，不靠换工具绕过授权。

## 识别状态与改动归属

进入仓库或切换工作位置后，先确认仓库根目录、当前分支或 detached HEAD、已有改动。可使用：

```bash
git rev-parse --show-toplevel
git status --short --branch
git diff
git diff --cached
```

按当前操作读取必要范围；未跟踪文件不出现在普通 diff 中，需要单独检查内容。涉及 worktree、远端或进行中的操作时，再检查相应状态。

- 区分已有修改、本任务新增修改以及执行中出现的其他修改。归属来自任务、初始状态和实际编辑证据，不能仅凭作者、文件名或“我碰过这个文件”推定。
- 无关修改保留并继续工作。同一文件混有不同来源的修改时，按差异块判断；归属不清且影响操作时询问，不用整文件暂存、覆盖或回退来省略判断。
- 暂存区也是需要保留的既有状态。发现他人已暂存内容时，不把它一起提交，也不为方便自行清空暂存区。
- 检查是否已有 merge、rebase、cherry-pick 等操作及冲突。先确认该操作与当前任务的关系，再决定继续、终止或保留；不要把未知的中间状态当作需要“修好”的环境。
- 后续修改分支、历史或暂存区前，核对决定该操作的状态仍有效。出现并行修改、切换位置或命令失败时重新检查相关状态；不在每个只读命令前重复全仓扫描。

## 破坏性操作的执行前置条件

对 `clean`、`reset`，以及其他会丢弃修改、改写历史或删除引用、工作区的操作，必须先完成以下步骤，再执行实际变更。包括用于丢弃内容的 restore/checkout、amend/rebase、强制推送、分支或 worktree 删除等；不能仅因没有 force 参数就跳过。

1. **dry-run 预检**：有原生 dry-run 时必须使用，路径、目标和过滤选项与计划执行的操作一致；没有原生 dry-run 时，做等效的只读影响检查，列明将改变或丢失的引用、提交、暂存内容和文件。检查结果必须被实际阅读，不能只确认退出码。无法确定影响范围时停止，不执行试探性破坏操作。
2. **新建备份分支**：每次操作前，针对将被改写或删除的提交端点新建唯一命名的备份分支，并核对其指向；只影响当前工作区时至少备份当前 HEAD。不能以已有分支、reflog 或“已推送”代替本次新建备份分支；涉及多个独立端点时分别保留。
3. **补齐分支无法保存的状态**：备份分支只保存提交历史。操作会丢失未提交、仅存在于 index、未跟踪或忽略内容时，还须在操作影响范围外保存相应内容和恢复所需状态，并核对覆盖范围。不能把创建分支当作已备份这些文件，也不能为备份擅自把他人修改提交到当前分支。
4. **核对后执行**：预检、备份成功且授权覆盖实际影响后才执行；备份失败、没有可指向的提交或无法可靠保存受影响状态时停止并报告。预检后相关状态发生变化时重新检查，并使备份覆盖新的执行前状态。

这些步骤是已有授权下的必要保护，不额外授予执行、扩大范围或删除备份的权限。具体检查与备份方法见[操作参考](references/operations.md#破坏性操作的预检与备份)。

## 暂存与提交

1. 按一个可解释的变更意图划定提交范围，遵循项目的提交约定和验证要求。不要把所有脏文件都当作本任务产物。
2. 检查候选文件的完整相关差异和现有暂存内容。已确认整个文件都属于本次提交时，使用显式路径暂存；同文件混合修改时使用差异块暂存。非交互环境的处理见[操作参考](references/operations.md)。
3. 执行 `git add -A` 后，必须用 `git diff --cached --name-status` 检查完整 staged 文件列表，逐项核对路径、增删状态与本次提交范围，不能直接接着 commit。再检查最终 `git diff --cached`，确认内容、删除、文件模式和新增文件都符合本次提交。显式 `git add` 路径不会排除之前已暂存的其他内容；`git add -u` 也不是按任务筛选。
4. 对实际提交内容取得相称的验证。部分暂存后，工作区测试结果不一定代表将提交的快照；差异可能影响结论时，对提交候选快照验证，不能为了测试擅自移走他人的修改。
5. 使用非交互提交方式，按下节规范撰写消息。提交被 hooks、身份、签名或其他配置阻止时，先定位原因；不要为取得成功自行跳过检查或更改全局配置。
6. 核对新提交的内容、分支及剩余状态，确认范围外修改仍被保留。工作区有无关修改可以正常交付。

提交失败后先确认是否已生成提交、hooks 是否修改了文件，再决定下一步。修改最新提交属于历史重写：只有授权涵盖这一动作，且确认提交归属与发布情况后才 amend；“最近的一条”不等于“本任务的一条”。

### Commit message 规范

- **格式**：除用户或项目有其他明确要求外，使用 Conventional Commits：`type(scope): 摘要`；scope 在有明确模块范围时填写，否则用 `type: 摘要`。type 使用与变更相符的 `feat`、`fix`、`docs`、`refactor`、`perf`、`test`、`build`、`ci`、`chore` 或 `revert`。标题单行，正文与标题之间留一个空行；默认不因近期提交格式随意而放弃规范。
- **语言**：用户明确要求优先；没有明确要求时，查看最近若干条有代表性的提交，分别参考标题和正文的语言。项目有明确的提交语言约定时遵循约定；近期语言混用且无明显惯例时沿用当前交流语言。type、scope、代码标识和规范 trailer 保持其约定写法，不机械翻译。
- **标题内容**：准确概括这一提交的主要变化，说明改变了什么；避免只有“更新”“修复问题”或文件列表。一个标题无法概括的独立意图应先检查是否需要拆分提交。
- **正文内容**：说明变更内容、原因与影响；涉及行为、接口、配置或兼容性时说明相应变化及关键取舍。简短变更可用一个短段落表达，不要求固定小标题或重复标题。按验证需要说明实际执行的检查与结果、未验证的限制，不把计划或推测写成已完成。
- **破坏性兼容变更与附注**：有不兼容变更时按 Conventional Commits 使用 `!` 或 `BREAKING CHANGE:` 并说明影响与必要迁移；issue、签署或协作者 trailer 只依据真实关联和项目要求填写。消息描述仓库变更，不混入无关操作日志、凭据或本地工作记录。

示例采用英文标题、中文正文；实际语言按上述顺序选择：

```text
fix(parser): preserve empty fields in quoted input

修正带引号输入中空字段被跳过的问题，使解析结果保留原始字段位置。
普通非空字段的处理方式保持不变。

验证：相关解析用例通过。
```

## 分支与 worktree

- 局部且无冲突的任务可以原位完成。并行任务、共享文件冲突或独立验证需要隔离时使用 worktree；先识别已有工作区和宿主提供的管理方式，避免重复创建。
- 创建前明确起点和目标分支。新 worktree 通常从提交建立，不会自动携带当前未提交修改；需要这些修改时明确其范围与转移方式。
- 所有编辑、暂存和验证都指向目标工作区。shell 的 `cd` 不保证其他工具随之切换，必要时使用明确的工作目录或绝对路径。
- worktree 独立保存工作区、index 和 HEAD，但共享多数引用和默认仓库配置。不要为了使用一个分支而强行解除其他工作区的占用；detached HEAD 也可能是宿主有意创建的状态。
- 清理前核对实际创建归属、活跃使用情况、未提交和未跟踪内容、需保留的忽略文件，以及提交是否已有可靠引用或已整合。目录名称、文件年龄、PR 已创建或工作区干净都不足以证明可删除。
- 合并完成不自动授权删除其他工作区或分支；清理范围遵循当前任务和既有约定。删除被拒绝时检查原因，不直接增加 force。`worktree prune` 清理失效登记，不等于删除工作区内容。

## 同步、整合与推送

- 先识别源、目标和提交范围。不要默认远端叫 `origin`、目标叫 `main`，也不要把 upstream 自动当作功能分支的合并基线。
- 需要远端现状时获取相应引用；fetch 更新本地远端跟踪信息，不代表已整合，也不证明允许覆盖远端历史。不要为一个本地提交固定附带 fetch 或 pull。
- 根据用户和项目约定选择 fast-forward、merge、rebase 或 cherry-pick。`pull` 会获取并整合，行为受参数和配置影响；整合前确定策略，而不是用裸 `pull` 试到成功。
- rebase、amend 等会改写提交标识；确认涉及的历史、消费者与授权。解决冲突时理解两侧意图，不用全局 ours/theirs 选择代替语义判断；尤其注意 rebase 下两侧含义。详见[操作参考](references/operations.md)。
- 整合后验证实际结果。已有测试若针对整合前的树，不能直接证明整合后的组合有效；是否复测以及范围取决于实际变化。
- 推送前核对远端地址、源提交、目标引用和全部将发布的提交。推送分支会发布目标缺少的可达历史，不仅是“刚写的那一个提交”。
- 遇到非 fast-forward 拒绝，先调查分叉；不要把失败自动升级为强推。授权明确要求重写远端时，检查将被替换的历史，并使用绑定已审查目标值的 lease；lease 保护状态一致性，不证明覆盖内容已获授权。

## 撤销、丢弃与恢复

先定位要撤销的变更、当前保存位置，以及必须保留的后续修改，再选择动作：

| 目标 | 处理方式 |
| --- | --- |
| 撤销本任务的部分未提交修改 | 对当前内容做针对性反向编辑或补丁，保留同文件其他修改 |
| 取消暂存、保留工作区内容 | 只调整目标路径或差异块的 index；先检查是否有需要保留的暂存版本 |
| 撤销已发布提交的效果 | 通常使用 revert 新增反向提交，检查依赖、后续修改和冲突 |
| 改写本地历史或丢弃指定内容 | 在授权范围内确认引用、路径和将丢失的状态，再选择 reset、restore 等具体模式 |
| 找回移动前的引用或丢失的提交 | 从 reflog、现有引用等定位对象，核实后建立恢复引用或提取所需内容 |

“撤销刚才的修改”若已有明确对象，可直接按该范围处理；有多种解释且会影响保留内容时再询问。不要把它扩大成整个文件、整个暂存区或整个仓库的恢复。

stash 会保存并移走一部分当前状态，其内容覆盖由参数决定；不是只读备份。reflog 记录引用变化，不保证能恢复未进入 Git 对象库的文件。发生丢失或错误操作时先保留现场、调查恢复来源，避免继续清理或重写掩盖证据。具体语义见[操作参考](references/operations.md)。

## 核对与交付

按目标核对结果，不以“命令返回成功”或“工作区干净”代替验收：

- 提交：提交标识、内容与所在分支正确，剩余修改符合预期。
- 整合或推送：目标引用实际指向预期结果；本地提交成功不等于已推送。网络结果不确定时查询远端再决定是否重试。
- 恢复或清理：目标内容已恢复或指定对象已移除，需要保留的内容和引用仍在。

报告实际完成的动作、相关提交或分支、验证结果，以及影响接续的剩余状态。满足当前目标后停止。
