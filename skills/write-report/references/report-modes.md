# 报告模式

本文件是报告结构和字段说明，不是交付物。生成报告时必须把每个字段替换为具体内容；无法取得的数据写“未采集”并说明原因。

## 阶段总结 / 多提交

面向一个开发阶段、多个 commit 或多个候选方案的组合报告：

- 报告范围、日期、环境、数据集或测试对象。
- 摘要表：提交或方案、关键结果、状态。
- 按“已合入”、“本地已验证但未合入”和“未采纳”分组，每组保留 commit hash 或分支标识。
- 每个方案区分初测与复测；初测与复测不一致时并列，并说明不可复现或噪声结论。
- 建议和取舍与事实分离；给结论时说明依据、代价、兼容性和剩余风险。
- 提供原始证据路径、运行脚本或日志位置，确保审计可回放。

## 普通 commit / 代码

面向读者描述、介绍或解释 Git commit 或编写的代码：

- 从程序行为入手：说明改动后的行为、触发条件、影响范围。
- 实现细节只有在解释行为、原因或副作用时才出现；不把代码逐行复述当作报告。
- 给出 commit hash、涉及文件或模块、行为变化和验证依据。
- 若没有行为变化，明确说明当前信息范围和已知限制。

## Bugfix / 正确性修复

必须覆盖：

- 预期行为。
- 实际行为。
- 造成差异的原因。
- 采用的方案或补丁。
- 验证方式、结果和残余触发条件。

每个字段使用可核验的证据；原因分析是技术推断，应标明依据，不写成必然结论。

## 性能提升

必须覆盖：

- 影响性能的根本原因。
- 采用的方案。
- 方案是消除根因还是参数化 workaround；若是后者，明确标注。
- 修复前与修复后的性能数据。
- 数据表格和完整测试条件。

测试条件包括工具或入口版本、commit 或代码版本、运行环境、输入与参数、运行次数、并发或顺序模式，以及原始输出路径。

表格列名和布局按数据结构选择；表内必须能表达：

- 比较对象或指标。
- 参与比较的数值或状态。
- 变化量与方向（适用于对比场景）。
- 单位或度量口径。
- 测试条件；可以放在表列、表下说明或通过唯一标识关联。

如果报告中摘要使用约数或范围，正文必须保留对应的原始数据表。

## 副作用

列出代码调整导致的预期之外行为变化：

- 说明该变化由哪项调整引入。
- 区分已观察到的副作用与未验证的可能影响。
- 未观察到时，写“测试范围内未观察到”，并说明测试范围。
- 兼容性、默认值、索引格式、构建成本、内存或磁盘占用变化单独列出。
