# 编写技术报告

## 适用范围

- 本 skill 用于代码、Git commit、bugfix 或性能变更的技术报告。
- 不用于普通文章、营销文案、用户故事等非技术类文档；用户明确要求时另行处理。
- 默认在对话中输出 Markdown 报告；用户指定文件时才写入文件。

## 工作流程

1. 确定报告对象和模式：普通 commit/代码、bugfix、性能提升。
2. 收集证据：commit hash、diff、文件路径、测试输出或基准数据；只使用可核验的来源。
3. 按对应模式组织内容，见 [references/report-modes.md](references/report-modes.md)。
4. 交付前执行语言检查和证据检查；不完整的数据明确标注缺失范围，不用模糊比较替代。

## 语言规则

- 事实指可由代码、diff、输出、文件、配置或测试结果支持的陈述；技术推断必须标明依据，不能伪装为事实。
- 用户未要求评价时，不引入好坏、优劣、态度或价值判断；用户要求评价时，单独成节并说明依据。
- 保留对象、单位、范围、条件和时间上下文；`索引大小 -3.1%` 不能简写成 `索引 -3.1%`。
- 使用书面化技术表达，不使用口语、修辞、比喻或类比解释概念。
- 不使用占位符、待补充内容或“原性能：低；修复后：高”这类不可核验的空泛比较。
- 缺失的数据写“未采集”并说明原因，不以推测填充。

## 数据表达

- 有数据时使用表格，并附上测试条件、参数、工具或入口版本、commit 或代码版本、运行环境、输入、运行次数和原始输出路径。
- 数字保留单位和测量维度；对比写明基线、修复后数值、变化量和方向。
- 原始输出优先指向持久文件；无法提供时说明数据来源和限制。

## 副作用

- 明确区分预期行为与非预期行为变化。
- 报告代码调整导致的预期之外行为变化，无论好坏；测试范围内未观察到时写“测试范围内未观察到”，不写“没有副作用”。
- 未验证的边界明确标注为未验证，不推断为无影响。

## 完成检查

- 每个结论都能追溯到证据来源。
- 没有占位符或空泛比较。
- 没有未经请求的评判或态度。
- 数据、单位、测试条件完整。
- bugfix 报告覆盖预期行为、实际行为、原因、方案和验证；性能报告覆盖原因、方案、前后数据和条件。
