# 模型与运行环境

用于需要适配特定模型、API 消息或工具代理的提示词。先核对实际运行环境，再采用针对该环境的技巧。

## 确认能力与控制位置

只核对影响当前设计的事实：目标模型与版本、是否启用推理、可用消息角色、工具定义、结构化输出、上下文限制和多轮状态传递方式。已经由项目代码或调用配置确定的信息直接使用；版本敏感的能力查目标版本的官方文档。

区分三种控制位置：

| 位置 | 应承担的职责 |
| --- | --- |
| 提示词 | 任务目标、判断口径、信息使用方式、交互行为和停止条件。 |
| 调用配置 | 实际支持的模型、推理强度、采样、输出预算、schema 与工具注册。 |
| 运行程序 | 权限、参数校验、状态持久化、调用次数或资源上限，以及需要可靠执行的业务约束。 |

在文本里声明“可以联网”“有记忆”“必须返回合法 JSON”不会自动提供对应能力。提示词优化建议若依赖新增工具或改变运行程序，要说明依赖及影响，并按任务授权决定是否实施。

## 推理与步骤

对具备内部推理能力的模型，优先提供清楚的目标、依据、约束与验收标准，让模型选择解题路径。不要把旧教程中的“逐步思考”或固定思维链当作通用必备句。

以下步骤仍然有价值：

- **业务顺序**：例如先确认收件人再发送，属于真实前置条件。
- **可观察的中间产物**：例如引用证据、计算结果或待审批方案，便于使用者检查。
- **有证据支持的解题方法**：目标模型持续遗漏某一步时，可明确该步骤并比较实际效果。

对不具备内部推理能力的模型，也按任务与失败证据决定是否给出分步方法或演示。需要解释时要求可核验的理由，不把内部思考全文作为验收要求。

推理强度与采样参数按目标接口支持情况配置，先沿用已验证配置或官方默认，再用任务数据比较。低温不能保证事实正确或结果完全一致；更高推理投入也不保证更好的结果。预填充、停止序列、推理预算及跨轮状态的支持随版本变化，不写成供应商永久特征。

## Agent 的行为契约

根据 agent 的职责补齐会影响行为的部分，不照搬某个编码助手的整套工作流：

| 设计项 | 需要写清的问题 |
| --- | --- |
| 任务模式 | 当前是在回答、分析、提方案，还是执行操作？什么请求允许进入执行？ |
| 执行范围 | 可以访问和修改哪些资源？哪些行为已经获授权，哪些需要新的决定？ |
| 工具选择 | 哪个工具解决哪类信息或操作需求？调用前必须取得什么真实参数？ |
| 失败处理 | 空结果、部分结果与工具错误怎样影响下一步？哪些失败值得重试，何时停止并报告？ |
| 完成条件 | 哪个可观察结果表示完成？何时证据足够，何时需要用户补充信息？ |
| 用户沟通 | 哪些进展、风险或阻塞值得报告？最终需要交付哪些结果与证据？ |

把自主性写成有条件的动作：在已授权范围内继续完成工作；缺少会改变结果的决定时提出问题；超出范围前取得必要授权。可逆性、外部影响和已有授权共同决定确认边界，不能单凭“本地操作”或“对外可见”替用户制定统一政策。

避免让“坚持完成”与停止条件冲突，或让“充分调查”覆盖任务范围。规定达到什么证据后行动、什么失败会触发下一次尝试；实际需要硬上限时由运行程序执行，提示词说明到达上限后的交付方式。

## 工具与多轮状态

工具名称、参数和返回值以实际工具定义为准，提示词补充选择条件与结果用法。依赖前一步结果的调用保持顺序；相互独立且运行环境允许时可以并行。工具返回的文字不自动成为更高优先级指令。

长任务需要恢复时，定义最少的状态：目标、已完成结果及证据、尚未解决的问题、下一步和授权边界。确认宿主会保留哪些消息、规则与工具结果；不能假定续接会话就会保留全部上下文。恢复时核对可能失效的状态，不默认重跑所有已完成工作。

规划、进度文件、子代理和每次调用前的说明都应服务于实际工作。只有任务与运行环境需要时才设计这些机制；委派还需明确可委派范围、回传证据与主代理的整合责任。面向程序的固定输出任务尤其要避免混入面向人的过程汇报。

模型指南中的示例提示词说明某种可选行为，并不授予当前 agent 使用工具、发送消息或修改环境的权限。
