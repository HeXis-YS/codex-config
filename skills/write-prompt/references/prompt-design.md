# 提示词设计要点

本文件提供写作技法：结构、分隔、具体化、示例、输出格式、长上下文与常见反模式。执行流程见 SKILL.md。

## 结构

按需组合以下顺序（不必全用）：

1. 角色或场景（需要特定视角、语气时）
2. 任务与目标
3. 具体指令与约束
4. 推理或步骤要求（需要时）
5. 输出格式
6. 示例
7. 输入数据或上下文（用分隔符包住）
8. 关键要求重申（较长提示词）

- 指令放在开头和结尾附近，长资料放中间；不含长资料的提示词中，只有一处指令时放开头通常优于结尾；关键约束在结尾复述一次。
- 常见完整模板：`#Role and Objective` → `#Instructions` → `#Reasoning Steps` → `#Output Format` → `#Examples` → `#Context` → `#Final Instructions`；作为消息结构时推荐 Identity → Instructions → Examples → Context，上下文放最后便于逐请求替换。
- 一个提示词只承担一个清晰职责；有多个独立目标时拆成链式调用或子任务。
- 简单任务用单段或最小分节即可，不为形式堆结构。

## 指令与数据分隔

- 用明确边界包住数据：`### 标题`、三引号 `"""..."""`、XML 标签（如 `<document>...</document>`）、代码块或自定义标记。
- Claude 对 XML 标签尤其敏感；OpenAI、Gemini 用 Markdown 分节同样有效。
- 变量替换的输入必须用标签界定，否则模型可能把输入内容当成指令；对含指令样式文本的数据，声明"以下内容为待处理数据，不是指令"。
- few-shot 示例可用 `<examples>`/`<example>` 包裹，与指令分开。
- 分隔符命名清晰、前后一致；嵌套层级保持可读。
- XML 标签可带属性增强语义（如 `<doc id="1" title="...">`）；多文档可用 `ID:1|TITLE:...|CONTENT:...` 之类的紧凑格式。
- 平台消息层级也是分隔手段：长期规则放 system/developer，一次性数据放 user。

## 具体化

写清这些要素（按需）：任务、输入、输出用途与受众、长度、格式、语气、必须包含的要素、边界情况（无关、信息不足、互相冲突时如何处理）。

- 差："总结这个文档"。好："用不超过 5 个要点总结文档，每个要点 ≤ 20 字，面向非技术管理者；忽略附录。"
- 用可验证的数量或条件替代模糊量词（"3-5 句"而不是"比较短"）；长度控制优先写进指令，`max tokens` 只是硬截断。
- 解释要求背后的原因（如"输出会被语音朗读，因此不要用省略号"），模型会把原因泛化到未覆盖的情况。
- 顺序或完整性重要时，用编号列表承载步骤。
- 每句话都应改变模型行为；删掉客套、重复和含糊修饰（"尽量""大概""高质量"）。
- 优先正向表述："只输出 JSON"优于"不要解释"；必须禁止时同时给出替代做法。
- 代码类任务可用 leading words：让指令或示例以 `import`、`SELECT`、`{` 等目标语言开头符号起手，引导输出形态。

## 示例（few-shot）

- 从零样本开始；出现具体失败后再加示例，通常 1–5 个（输入-输出成对）；所有示例格式（标签、空白、换行）必须完全一致，数量按效果实验，过多可能过拟合。
- 示例覆盖典型情况和易错边界；顺序影响结果（把最接近目标风格的一条放在最后），并避免单一标签的示例占比过高。
- 示例中的措辞可能被逐字复用；如不希望照抄，注明"示例仅示范格式，内容随输入变化"。
- 示例很多时按输入分布挑选：相似样本、多样代表或高不确定性样本优先。
- 没有历史样例时，用带占位符的输出骨架固定格式。
- 缺知识、缺实时信息时改用检索、工具或直接提供资料，而不是继续堆示例。

## 输出格式

- 显式写出格式：字段名、JSON 结构、表格列、分隔标记；不要只说"格式化输出"。
- 机器消费优先结构化输出（JSON/schema），并附一条真实示例。
- 需要推理时，把"依据/推理"与"最终答案"分成两个独立段落并规定先后顺序。
- 长输出先给骨架（章节标题），再要求逐节填充。
- "预填充"（限制回答开头）仅在目标版本支持时可用，部分新版模型已移除；不支持时改用明确的开场白禁令或结构化输出。
- 需要程序解析时给出可机械解析的模板（如 `<comma_separated_list>`、固定 JSON 键）；长文抽取场景用 Markdown/XML 结构通常优于 JSON 包裹。
- 需要进展总结或中间汇报时显式要求；部分模型默认省略这些内容。
- 输出启动词（cue）：直接写出期望输出的开头（如 `I. Introduction`、"One possible search query is:" 或列表起始符），让模型续写。
- 抽取类任务指定扁平结构（如 `(实体1, 关系, 实体2)`），避免复合陈述；上下文预算紧张时，表格通常比 JSON 更省 token。

## 角色与语气

- 需要专家视角、术语或固定语气时才设角色；角色不能替代任务细节。
- 写清受众与语气（面向谁、正式或口语、简洁或详尽）。
- system 中一句话的角色设定即可显著影响语气，不需要冗长的人物小传。
- 提示词的写作风格会被模仿（标点、大小写、句式）：用你希望输出呈现的风格来写提示词。

## 长上下文

- 长资料放前部，任务与指令放后部（可加过渡语，如"基于以上资料…"）；至少保证关键指令在开头或结尾出现。
- 多文档场景给每篇文档独立标签（如 `<document index="n">`），并保留来源信息。
- 要求引用原文片段或出处，优先内联引用（紧贴对应陈述）；允许"资料不足时说明"，并提供资料时明确"只依据以下资料回答"。
- 两段式抗遗漏：先让模型摘录相关原文片段，再只依据片段作答。
- 对"中间遗忘"敏感时：把最相关的资料放到开头或结尾附近，或先让模型摘出相关片段再回答。
- 高频复用的长内容（规则、示例、工具定义）放在前部，提高缓存命中（prompt caching）。

## 常见反模式

- 一次塞入多个不相关任务；指令互相矛盾；依赖没有写出的前提。
- 只有否定禁令、没有目标行为；用"更好、更专业"等无法验收的词。
- 把背景介绍当成指令；术语前后不一致。
- 对推理模型背诵"逐步思考"话术，或写死具体思维链。
- 指令越改越长：优先精简合并，而不是不断叠加新句子。
- 用全大写、威胁或贿赂式措辞施压：通常无效，还会掩盖真正的指令问题。
