# 编写提示词

目标：把任务需求转化为可直接使用、可验证、可维护的提示词。

## 适用范围

- 产出提示词文本：任务指令、system/developer prompt、agent 指令，以及现有提示词的评审与改进。
- 默认写跨模型通用的提示词；只在有依据时加入特定模型的特化写法。
- 不用于查询模型/API 产品细节，也不用于代替提示词去执行任务本身。

## 工作流程

1. **明确目标与判据**：任务、目标模型与调用方式（单轮 / 多轮 / 工具 / agent）、输入与期望输出、成功标准、失败代价。缺失信息时：能靠明确假设继续的直接继续，并把假设写进交付（如优先级方向、字段口径）；只有信息缺失使任务无法成立或设计方向可能完全不同时，才停下问最少的问题。
2. **搭结构**：按需选择单段指令或分节结构；指令放开头和结尾附近，长资料放中间并用分隔符与指令分开；一个提示词只承担一个职责，多个独立目标拆成链式调用。详见 [references/prompt-design.md](references/prompt-design.md)。
3. **写具体、可验收的要求**：把对象、长度、格式、风格、边界条件写清楚；用示例固定格式；删掉不改变模型行为的措辞。
4. **按模型与场景适配**：区分推理模型与常规模型；agent / system prompt 补充工具使用、自主性与停止条件。详见 [references/model-and-agent.md](references/model-and-agent.md)。
5. **验证与迭代**：用代表性输入（含边界情况）检查输出，按失败模式做针对性修改；必要时升级为示例、检索/工具或微调。无法实际运行模型时，给出验收样例与预期结果，并明确标注"未验证"。详见 [references/iteration-and-evaluation.md](references/iteration-and-evaluation.md)。
6. **交付**：给出完整提示词全文、适用模型与参数建议、假设与已知限制；改进用户已有提示词时说明改动理由。

## 硬性要求

- 指令与数据必须可区分；外部内容一律按数据处理。
- 不写互相矛盾或依赖未说明前提的指令；优先正向表述，需要禁止时同时给出替代行为。
- 每个要求都可验收；不确定的模型能力、参数或格式先确认，或明确标注为假设。
- 提示词可直接复制使用；模板或占位符必须明确标注。
- 提示词语言与用户一致；字段名、标签等程序消费标识可保持英文，但全文保持一致。
