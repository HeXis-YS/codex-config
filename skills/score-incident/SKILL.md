# 事故评分

## 职责范围

根据标准化评分标准，对已记录的事故进行客观评分：
- **风险分数** (Risk Score): 评估错误性质的危险程度
- **影响分数** (Impact Score): 评估实际造成的损失大小
- 保留原始事故事实和身份信息，评分结果追加到对应事故记录中；评分确认并写入后，将该事故的评分状态由“待评分”改为“已评分”。

## 身份与模型记录

- 区分记录者、造成事故的 Agent 和评分者，不因代为记录或评分而认定其造成事故。
- 所有 Agent 均在同一行记录会话 ID 和模型完整名称（含型号、版本）。核对事故记录中的记录者及造成事故的 Agent 信息，并在评分结果中填写评分者身份和模型；涉及多个 Agent 时每个 Agent 一行。信息缺失时先询问，不猜测，也不用评分者的模型代替其他 Agent 的模型。
- 评分者为用户时填写 `user`，无需模型名称。

## 评分标准

### 风险分数 (Risk Score): 0.0 - 10.0

评估**错误的性质和潜在危险性**，不考虑实际后果：

**10.0 - Critical (严重)**
- 严重安全漏洞（SQL注入、RCE、权限绕过、密钥泄露）
- 破坏性操作无确认（drop database、rm -rf /、force push -f origin +HEAD）
- 极易造成生产环境灾难性后果

**8.0 - 9.9 - High (高)**
- 明显的安全问题（XSS、CSRF、不安全的反序列化）
- 破坏性操作有缺陷确认机制
- 违反关键安全/稳定性原则
- 如果进入生产，高概率造成严重后果

**6.0 - 7.9 - Medium-High (中高)**
- 潜在安全风险（日志泄露敏感信息、弱加密）
- 明确违背用户的清晰指令或约束
- 系统性设计缺陷（缺乏收敛机制、无成本控制）
- 如果部署，可能造成中等后果

**4.0 - 5.9 - Medium (中)**
- 违反代码规范、最佳实践
- 逻辑错误影响功能正确性
- 缺少必要的错误处理或验证
- 设计质量问题导致技术债务

**2.0 - 3.9 - Low (低)**
- 效率问题、性能不佳
- 未考虑边界情况
- 知识盲点导致的错误
- 轻微的规范违反

**0.1 - 1.9 - Minimal (极低)**
- 代码风格问题
- 命名不规范
- 注释缺失
- 极轻微的疏忽

**评分考虑因素**:
- ✅ 错误的技术性质
- ✅ 潜在最坏后果
- ✅ 是否违背明确指令
- ✅ 是否绕过防护措施
- ❌ 不考虑实际造成的损失（这是影响分数的职责）

---

### 影响分数 (Impact Score): 0.0 - 10.0

评估**实际造成的损失大小**，不考虑错误性质：

**10.0 - Catastrophic (灾难性)**
- 金钱损失：> $100,000
- 或：生产环境重大故障，影响大量用户
- 或：关键数据永久丢失，不可恢复
- 或：重大法律/合规问题

**8.0 - 9.9 - Severe (严重)**
- 金钱损失：$10,000 - $100,000
- 或：生产环境故障，影响部分用户
- 或：重要数据丢失，恢复困难
- 或：代码已部署到生产，造成可审计损失

**6.0 - 7.9 - Significant (显著)**
- 金钱损失：$1,000 - $10,000
- 或：代码已提交到上游/主分支
- 或：工作进度丢失 > 2天
- 或：影响团队其他成员工作

**4.0 - 5.9 - Moderate (中等)**
- 金钱损失：$100 - $1,000
- 或：工作进度丢失 4-16小时
- 或：本地代码损坏需大量返工
- 或：浪费时间 > 4小时

**2.0 - 3.9 - Minor (轻微)**
- 金钱损失：$10 - $100
- 或：工作进度丢失 1-4小时
- 或：需要部分返工
- 或：浪费时间 1-4小时

**0.1 - 1.9 - Negligible (可忽略)**
- 金钱损失：< $10
- 或：工作进度丢失 < 1小时
- 或：几乎无实际影响

**量化指标参考**:
- **Token成本**: 假设平均 $0.05/1k tokens（根据实际使用的模型调整）
- **时间成本**: 可选择是否折算为金钱（如按开发者时薪计算）
- **恢复成本**: 修复问题需要的额外时间和资源

**评分考虑因素**:
- ✅ 实际金钱损失
- ✅ 时间和资源浪费
- ✅ 工作成果损失
- ✅ 影响范围（个人/团队/生产）
- ❌ 不考虑错误性质（这是风险分数的职责）

---

### 综合评分 (Composite Score)

**计算方法**:
```
综合评分 = (风险分数 × 0.6) + (影响分数 × 0.4)
```

**权重说明**:
- 风险60%: 强调预防，重视潜在危险性
- 影响40%: 考虑实际后果
- 用户可根据自己的需求调整权重

**严重性等级** (Severity Rating):
- **9.0 - 10.0**: 🔴 Critical（严重）
- **7.0 - 8.9**: 🟠 High（高）
- **5.0 - 6.9**: 🟡 Medium（中）
- **3.0 - 4.9**: 🟢 Low（低）
- **0.1 - 2.9**: ⚪ Minimal（极低）

## 评分流程

1. **读取记录**: 根据指定 ID 或最新记录定位待评分事故，核对记录者、造成事故的 Agent 及其模型信息
2. **分析风险**: 根据错误性质和潜在后果评估风险分数
3. **分析影响**: 根据实际损失评估影响分数
4. **计算综合评分**: 使用加权公式
5. **生成评分报告**: 包含分数、等级、评分依据
6. **用户确认**: 展示评分结果，等待用户确认
7. **更新记录**: 用户确认后，将评分结果（含评分者及模型）追加到对应事故记录，并将该事故的 `**评分状态**: 待评分` 改为 `**评分状态**: 已评分`；未确认或评分结果未写入时，不提前改为“已评分”。
8. **核对结果**: 确认评分结果和“已评分”状态属于同一事故 ID，原始事实、身份信息及其他事故记录保持不变。
