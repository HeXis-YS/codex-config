# 编写代码

## 建立实现契约

- 修改前读取适用指令以及相关代码、测试、配置和调用方，先理解项目既有模式。优先编辑和扩展现有文件与组件，不重写完整模块或建立平行实现。
- 从用户目标确定验收标准、必须保持的行为和验证方式。架构、公开契约、数据模式、身份认证、资金、迁移、删除、生产或 Live 等高风险改动，实施前明确关键假设、计划和验证方式。只有必要信息或授权无法从当前上下文确定，且自行假设会实质改变预期结果、任务范围、验收标准、公开契约、架构方向、风险等级或执行权限时，才暂停询问；其余任务范围内的可逆实现决策直接完成。
- 仅实施当前任务范围。不得混入无关重构、优化、迁移或功能扩展；范围外发现单独报告。
- 当前任务明确要求查找、排查或修复缺陷，或将 Bug、失败测试、CI 失败或用户反馈作为待解决问题时，直接定位并修复范围内根因，无需再询问是否修复。其他任务中偶然发现的缺陷只报告，不顺手修改。

## 设计最小完整方案

- 选择假设最少、代码侵入最小且能端到端工作的实现；定位根因，不接受临时修复、hack 或计划以后替换的过渡方案。
- 优先复用项目已有组件和依赖。新增包或自行实现通用能力前，先查阅现有库的文档与类型定义；成熟且维护良好的库能降低总体复杂度时优先使用。
- 需要选择通用设计时，采用项目既有模式和成熟产品验证过的约定，不从零发明协议、框架或抽象。只在减少真实复杂度、耦合或重复时新增抽象和配置。
- 保持模块职责和领域边界清晰，以可工作的最小版本渐进演进；不以未经验证的复杂设计替换现有可用行为。
- 对未发布、内部且无已知消费者的开发中代码，不新增旧行为兼容层、回退、别名或迁移；确认路径过时时直接删除。只有公开契约、外部消费者、持久化数据或活跃生产与验证流程构成真实要求时才维护兼容。
- 保持确定性并显式失败，不静默忽略错误或回退到未预期行为。未经授权不得改变已验证行为契约，也不得影响无关运行系统、生产环境或验证流程。

## 实施可维护、可接手、可审查的改动

- 将改动限制在必要模块并完成其实际影响面，保持现有架构和业务语义。同步更新受影响的调用方、清单、配置、测试、自动化和文档，删除被替代路径、死代码和失效配置，使项目在变更后仍保持内部一致。
- 将仓库作为后续 Agent 与人类工程师共同使用的持久工作界面。新增或改变组件、入口、契约、依赖、配置或开发流程时，沿用项目既有结构，并在最接近实现的位置通过命名、类型或接口、测试、脚本或最小文档表达职责和用法，使没有先前对话的 Agent 能定位改动点、理解约束、运行验证并继续开发。对自解释且不改变使用方式的局部实现，以代码和既有测试作为持久契约。
- 使人类工程师能从聚焦差异及其相邻契约判断改动目的、行为变化、风险和验证证据。保持变更边界清晰，分离独立关注点，并用受跟踪的代码、接口、测试、脚本、配置或文档固化关键约定，使审查者能从项目制品而非作者的隐式上下文理解它们。
- 在关键逻辑、设计决策、边界条件和非显而易见处添加准确注释，不为自解释代码添加复述式注释。
- 优化前先取得可观察或可量化证据，不凭直觉追加优化。

## 建立可重放的工作流

- 预期重复执行的构建、编译、测试、基准、数据准备、复现或诊断流程，先复用仓库内已有脚本、任务目标或框架。第一次只是临时探测但需要重跑时，最迟在第二次执行前固化持久入口，后续只通过该入口运行。
- 入口按需固定或校验工作目录、依赖、输入、参数、配置、环境前提、随机种子、缓存或构建状态与输出位置。在最接近的 README、项目指令或 `--help` 中说明用途、前提、调用和输出，使全新上下文中的 Agent 或开发者仅凭仓库即可发现并运行；同步删除被替代路径。
- 用于验证或决策的重复运行将原始输出写入唯一标识的持久文件，并记录入口版本、代码版本或工作区差异标识、输入、配置和环境。异常且足以改变结论的单次结果，通过同一入口复现后才作为证据；无法复现时调查原因。性能测试建立基线、重复运行，并同时报告结果分布与正确性指标。
- 项目声明的入口缺少工具、组件或依赖时，按项目的依赖和环境管理方式立即安装，可直接使用 `sudo` 安装系统级依赖，然后重跑原入口。只在实际安装受权限、网络或安全策略限制后，才保留错误并使用最小替代方案或报告阻塞，不切换到无关语言、自制工具或旁路流程。

## 取得验证证据

- 完成前取得与改动类型、风险和影响范围相称的证据。优先运行最小充分组合：相关既有测试、静态或类型检查、构建、格式或语法检查、引用搜索以及针对性行为检查；证据不足时再逐级扩大。
- 检查命令的实际输出、日志和报错，必要时与基线行为对比。文档、注释、纯删除、简单配置或已被静态工具完整约束的改动可用检查、搜索、解析或构建验证，不为满足形式新增测试。
- 只有测试保护稳定且有意义的行为契约，并对应可信回归路径时才新增或扩展测试；优先复用最近的既有测试。合理场景包括真实缺陷、非平凡分支与边界、公共 API 或协议，以及认证、资金和数据一致性等高风险逻辑。
- 不为覆盖率或流程仪式创建测试，不重复证明编译器、类型系统、框架或另一个测试能工作，也不测试没有独立行为或现实失败模式的常量、简单转发和样板代码。每项测试都必须能说明会捕获的具体错误并因正确原因失败。
- 删除功能时同步删除或更新其测试、快照、夹具和辅助代码，通过引用搜索、构建、静态检查及相关测试确认删除完整。只有拒绝旧行为本身是重要稳定契约时才保留负向回归测试。
- 完成前针对本次改动及其实际影响面做无上下文交接与审查充分性检查：从仓库能否定位相关入口、职责、依赖、运行和验证方法；从差异、接口、测试和相邻文档能否判断改动意图、行为变化、风险与证据。任一答案为否时，优先简化实现或补齐最接近的持久契约，然后重新验证。
- 非简单改动在验证前检查是否存在更简洁、更易维护的实现；粗糙则基于现有证据重写。确保相关既有测试通过，必要时更新文档，然后在验收标准满足后停止。
