# 技术报告

用于代码、Git commit、缺陷修复、性能变更和阶段总结报告的证据组织与完整性审查。以下要求同时适用于中英文报告；语言与语义保真要求遵循 [SKILL.md](../SKILL.md)。

## 范围与证据

- 确定报告对象、读者与模式，按对应小节组织内容。默认在对话中输出 Markdown 报告，用户指定文件时写入文件。
- 收集任务范围内的代码、commit hash、diff、文件路径、测试输出或基准数据，使结论能追溯到可核验来源。只润色已有报告时，保留其证据范围，并指出会影响结论的材料缺口。
- 观察事实与技术推断分别表述，推断说明依据。用户未要求评价时，不引入好坏、优劣或态度判断；用户要求评价时，单独成节并说明依据。
- 采用书面化技术表达，不用口语、修辞、比喻或类比解释概念。每个适用字段写入具体内容或准确的缺失说明，不保留占位符，也不用“原性能低、修复后高”代替可核验的比较。
- 明确知道数据未采集时，说明未采集及已知原因；仅缺少记录时，说明现有材料无法确认是否采集或结果如何。原因未知时如实说明。工作与验证状态的区别见[文体与用途](text-types.md#结论与工作状态)。

## 数据与比较

- 用表格呈现数据，列名和布局按数据属性选择。表内表达比较对象、数值或状态、单位或度量口径；比较场景还需包含基线、变更后数值、变化量与方向。
- 保留完整的测量对象，例如“索引大小下降 3.1%”，不能缩成“索引下降 3.1%”。
- 数据关联完整测试条件：工具或入口版本、commit 或代码版本、环境、输入、配置与参数、运行次数，以及并发或顺序模式。
- 每张表通过表列、表下说明或唯一标识关联其测试条件。报告开头的全局条件仅覆盖明确标注的共享条件。
- 提供持久的原始输出路径；无法提供时，说明数据来源与限制。缺少必要数据时明确缺失范围，不用推测或空泛比较填充。
- 摘要使用约数或范围概括测量结果时，正文保留对应原始数据表。原始数据不足时不自行概括数值；来源本身带有估计或不确定性时保留该属性，不把估计改成精确测量。

## 阶段总结 / 多提交

面向一个开发阶段、多个 commit 或多个候选方案的组合报告：

- 报告范围、日期、环境、数据集或测试对象。
- 摘要表：提交或方案、关键结果、状态。
- 按“已合入”、“本地已验证但未合入”和“未采纳”分组，每组保留 commit hash 或分支标识。
- 每个方案区分初测与复测；初测与复测不一致时并列，并说明不可复现或噪声结论。
- 建议和取舍与事实分离；给结论时说明依据、代价、兼容性和剩余风险。
- 提供原始证据路径、运行脚本或日志位置，确保审计可回放。

## 普通 commit / 代码

面向读者描述、介绍或解释 Git commit 或编写的代码：

- 从程序行为入手：说明改动后的行为、触发条件、影响范围。
- 实现细节只有在解释行为、原因或副作用时才出现；不把代码逐行复述当作报告。
- 给出 commit hash、涉及文件或模块、行为变化和验证依据。
- 若没有行为变化，明确说明当前信息范围和已知限制。

## Bugfix / 正确性修复

必须覆盖：

- 预期行为。
- 实际行为。
- 造成差异的原因。
- 采用的方案或补丁。
- 验证方式、结果和残余触发条件。

每个字段使用可核验的证据；原因分析是技术推断，应标明依据，不写成必然结论。

## 性能提升

必须覆盖：

- 影响性能的根本原因。
- 采用的方案。
- 方案是消除根因还是参数化 workaround；若是后者，明确标注。
- 修复前与修复后的性能数据。
- 数据表格和完整测试条件。

## 副作用

区分预期行为与非预期行为变化，报告代码调整导致的预期之外变化，无论好坏：

- 说明该变化由哪项调整引入。
- 区分已观察到的副作用与未验证的可能影响。
- 未观察到时，写“测试范围内未观察到”，并说明测试范围；未验证的边界标为未验证，不推断为无影响。
- 兼容性、默认值、索引格式、构建成本、内存或磁盘占用变化单独列出。

## 交付检查

- 对照所选报告模式，核对行为、原因、方案、验证或阶段状态等适用内容是否齐全。
- 每项结论能定位其来源；表格能关联条件与原始输出，缺失信息和结论限制已明确。
- 已观察结果、推断、用户要求的评价及尚未验证的影响有清晰边界。
