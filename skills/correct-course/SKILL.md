# 纠错模式

在保留现场的前提下，与用户重新建立对问题和下一步的共同理解。本次调用要求先暂停核对，再确认恢复；原任务已有的执行授权不替代这次确认。

## 停止并保留现场

停止推进原任务和新的写入，不自行撤销、提交或清理。已有进程仍在运行时，说明状态，按用户的停止要求和可安全中断的边界处理。

## 核对目标与依据

1. 简述已经做了什么、工作区与外部状态，以及原先理解的目标；区分观察事实、用户判断和待验证假设。
2. 围绕影响方向的关键分歧提问，不用安抚、辩解或立即行动代替核对意图。用户只调用技能且上下文不足以定位问题时，先询问需要纠正的具体偏差。
3. 在用户允许的范围内做解决分歧所必需的只读检查。事实前提按证据核对，偏好与范围由用户决定；指令表达明确不代表事实前提已经成立。

说明当前理解、证据与拟采取的下一步，将需要用户回应的问题在结尾集中编号列出。保持暂停，等待用户确认方向或明确要求继续。

## 确认后恢复

- 用户确认经核对的方向，或明确要求继续后，再推进已明确的工作。仍有会实质改变结果、范围、风险或权限的未决问题时，仅就这些问题求证；已确认事项不反复询问。
- 不把含糊的撤销要求自行解释为某种 Git 操作。方向确认后，清理本次错误方向产生且归属明确的改动与临时文件，保留用户既有内容；归属或清理范围不明时先确认。
- 被否定的方案不进入正式交付或持久规则；必要过程事实留在交接或用户要求的事故记录中。纠错调用本身不授权新增规则或事故记录。
- 完成上述确认后退出纠错模式，按已明确的范围继续任务；后续普通补充与纠正按其内容处理。
