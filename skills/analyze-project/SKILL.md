# 分析项目

## 建立交付契约

- 将交付物定义为有证据的技术报告，而不是实现。除非用户明确要求修改，否则不修改受跟踪的项目内容；安装环境依赖和写入本地运行记录不受此限制。
- 从用户目标提取会影响报告结论的未决问题。若范围宽泛，默认回答项目目的、架构与入口、关键执行路径、依赖、构建与测试状态、相关历史以及主要风险。
- 只调查回答这些问题所需的范围。把观察事实、基于证据的推断和仍未知的信息明确分开。

## 执行分析闭环

1. **确定边界**：读取适用的项目指令、README、清单和构建配置；检查工作区状态，避免把既有改动误当成项目基线。按需查看目录、入口、测试和相关 Git 历史，不做无目标的全量遍历。
2. **打通主路径**：识别并执行项目声明的构建、运行和测试入口。入口缺少工具、组件、库或原始运行时时，安装后重试同一入口；在取得实际安装失败证据前，不得静默放弃或改走旁路。
3. **追踪关键流程**：从真实入口沿调用、数据和配置边界读取代码，用最近的测试、示例和路径级历史验证理解。每个命令或实验必须回答一个会改变报告结论的未决问题。
4. **控制实验范围**：优先使用既有入口、测试、示例和直接运行。不得为扩大覆盖面、绕开遗留环境或替代受阻主路径而移植代码、切换语言、编写平行实现或自制测试框架。
5. **收敛并停止**：当报告问题已有与风险相称的证据时停止。不得仅因仍有可浏览的模块或历史而继续扩展调查。

## 处理写入与缺陷

- 将一次性探测结果和原始输出写入项目约定位置；没有约定时使用 `.codex/runs/`，不得把临时产物混入受跟踪源码。
- 仅当决定报告结论的关键问题无法由现有基础设施回答，且流程预期重复执行时，才创建最小、可长期复用的受跟踪入口，并遵循全局可复现工作流和提交规则。
- 只报告分析中偶然发现的缺陷，不顺手修复。只有用户当前任务明确要求查找、排查或修复缺陷时，才进入修复流程。

## 形成报告

- 先给出能直接回答用户目标的结论，再说明项目结构和关键流程。
- 为重要结论引用具体文件、符号、提交或命令结果；报告实际执行的构建和测试命令及其结果。
- 单独列出风险、证据限制和未验证假设。不得用未执行的命令、推测性行为或不可复现的异常结果支撑结论。
